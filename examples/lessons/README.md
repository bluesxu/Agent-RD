# lessons 写法示例

这里是两条**真实产出**的 lesson，来自已删除的项目一（短链服务）。
`wf-keep` 的 SKILL 正文只讲规则，这里提供「写成什么样才算合格」的实物参照。

## 为什么留着这两条

它们同时示范了四条筛选判据都满足是什么样子：

| 判据 | 这两条怎么满足的 |
|---|---|
| 适用于本次 diff 之外 | 「不要在响应前 destroy 请求流」对任何 Node HTTP 服务成立 |
| 有可追溯证据 | 都指到了具体机制（`IncomingMessage._destroy`、Node 的头值正则 `/[^\t\x20-\x7e\x80-\xff]/`） |
| 能写成未来动作 | 开头就是「**动作**：以后遇到 X 就做 Y」，不是感想 |
| 没有 canonical owner | Node 文档不会告诉你这两个正确决策组合起来会出 bug |

**最值得学的是它们怎么处理不确定性**：

- `destroy-before-respond` 明确划了**证据边界** ——
  「对照实验只在 Windows 环回上做过，真实有损网络上那个风险**未被证伪**」，
  然后把 lesson 拆成确定部分和不确定部分。
- `node-header-value-charset` 给了**精确的边界实测** ——
  `é` / `ÿ` / C1 区放行，U+0100 / 日 / emoji 拒绝，
  所以判据是 `code <= 0x20 || code === 0x7f || code > 0xff`，
  而不是含糊的「拒绝非 ASCII」（会误杀）或「拒绝 > 0x7F」（会漏）。

**一条写得含糊的 lesson 比没有更糟**：它会让下一个人以为这件事已经搞清楚了。

## ⚠️ 它们也示范了一个错误：`status` 被写成了终点

两个文件的 frontmatter 都是 `status: validated`。**这是违规的。**

`wf-keep` 规定 `observed` 是**初始值**，`validated` 只能
「在独立的后续任务中确实采用并验证成功时升级，补一次代表性证据」。

而项目一唯一的后续 feature（`test-seam`）**从来没有被建过** ——
不存在任何独立后续任务，所以这两条**是出生时就被直接写成 `validated` 的**。

**为什么不改掉**：留着比改掉更有教育价值。它是一个具体实例，说明
**状态字段是自己给自己写的，而没有任何东西检查它**
（同 KNOWN-ISSUES 的 A15：规则写在那里，没人照做，也没有东西发现）。

`wf-keep` 里那句「生命周期 observed → validated → retired 从未走过」，
真实情况不是「没人走」，是**有人直接写了终点**。

**你写 lesson 时**：初始一律 `observed`。想写 `validated`，
先回答「是哪个独立的后续任务用上了它、验证证据在哪」——
答不出来就不是 `validated`。
