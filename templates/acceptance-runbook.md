# 验收层运行手册 —— {feature-slug}

> **这份文件回答「怎么观察」，不回答「怎么实现」。**
>
> 由 **第 1 轮验收者**在验收结束时写，与 `acceptance.json` 并列，是一等产物。
> 后续轮次的验收者**只读这份 + `acceptance.json`**，不再从零摸索。
>
> ⛔ **边界（这条决定了 runbook 存在的合法性）**：
> 只写「怎么操作才能观察到每条 AC 的判定对象」，
> **绝不写**系统内部怎么实现、代码在哪、为什么这样设计。
> 前者是程序性知识，隔离它纯属浪费；后者是 验收层防 overfit 的核心价值，隔离它是刚需。
> 写的时候自问一句：**这句话会让下一个验收者猜到实现吗？**会，就删掉。

## 一、驱动契约

怎么把这个系统操作起来。写清楚**命令原文**，不要写「用浏览器打开」这种没法照做的话。

| 项 | 内容 |
|---|---|
| 服务地址 | {host:port，由编排者启动后给出} |
| 驱动方式 | {opencli browser / curl / CLI 命令 / …} |
| 会话模型 | {单 tab？需要登录态？每条 AC 之间要不要重置？} |
| 选择器策略 | {用什么定位元素：文本 / role / data-testid；哪些选择器不稳} |
| 证据存放 | `reports/evidence/eval-round{N}/` |
| 证据命名 | {如 `ac{n}-{步骤}-{描述}.png`} |

**启动到可观察的最短路径**（照抄就能跑起来）：

```
{逐条命令}
```

## 二、每条 AC 的固定观察步骤

对**每一条 agent 判定的 AC**写一段。machine 判定的只需注明 check 命令从哪跑。

### AC-{n} {名称}

- **操作序列**：
  1. {动作}
  2. {动作}
- **读什么**：{具体读哪个数值 / 哪块区域的文字，不是「看看对不对」}
- **截图什么**：{截哪一屏，命名}
- **判定口径**：{什么算通过 —— 数值精确匹配？区间？存在即可？}
- **已知坑**：{这一步最容易观察错的地方}

## 三、环境事实表

**实测结论，带日期。**这一节的价值是「不用再试一遍」。

| 事实 | 实测结论 | 测于 |
|---|---|---|
| {外部依赖 X 是否可达} | {可达 / 被登录墙挡住 / 限流} | {日期} |
| {哪些测试标的数据不足} | {列出来，省得下一轮再搜一遍} | {日期} |
| {已知阻塞点} | {现象 + 绕不绕得过} | {日期} |

> 环境事实随验收者退出就丢失了 —— 实跑里第 2 轮验收者重新试了一遍
> 「这个搜索框点不动」，直到外部指令到达才停。写在这里就不会重演。

## 四、报告模板

必填小节以脚本为准：`node <agentrd>/scripts/check-artifacts.js -Sections`。
当前验收层报告要求 `验收结论` / `逐条` / `收尾附录` 三节都有实际内容，
末行盖 `<!-- RD-DONE stage=eval artifact=eval-round{N} at={ISO8601} -->`。

每条 AC 的判定行格式：

```
### AC-{n} {名称}  ✅ pass / ❌ fail / ⚠️ blocked / ⏭️ skipped
- 判定方式: machine / agent
- 我做了什么: {实际操作}
- 我看到了什么: {实际观察到的值}
- 证据: {路径}
```

| 最后一次实测验证 | {日期} |
