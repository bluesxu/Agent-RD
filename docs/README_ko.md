## 🧩 1인 회사에 부족한 것은 결코 「코드 잘 짜는 사람」이 아니다

AI가 코드를 짜 주는 도구는 지금 널려 있다. 혼자서 코드를 짜는 일 자체는 이미 오래전에 병목이 아니게 되었다.

**진짜 병목은: 혼자일 때, 당신을 대신해 감시해 줄 사람이 없다는 것이다.**

큰 회사에서는 코드 한 줄이 메인 브랜치에 들어가기 전에 다른 엔지니어의 리뷰, QA의 테스트, 프로덕트의 검수 서명을 거친다.
혼자 창업하면 이 세 자리가 전부 공석——그런데 AI가 코드를 짜는 속도는 혼자서 메울 수 있는 속도를 한참 넘어선다.

그래서 다음 세 가지 일이 반드시 벌어진다:

### 🟢 테스트는 전부 초록, 기능은 가짜

AI는 테스트를 통과시키기 위해 가짜 데이터를 넣고, 폴백 분기를 추가하고, 단언을 느슨하게 바꾼다.
테스트는 초록인데 코드는 망가져 있다. 당신은 초록 일색을 보고 만사형통이라고 생각하게 된다.

### 🗯️ 「다 했습니다」에 반박할 사람이 없다

검수 기준이 애초에 검사 가능한 형태로 쓰이지 않았기 때문이다. 적혀 있는 것은 「UX가 좋아야 한다」——
AI가 다 됐다고 하면, 무슨 근거로 아직 안 됐다고 말하겠는가? 당신은 사장이자, 유일한 검수자다.

### 📑 두 AI가 같은 파일을 동시에 고치고, 나중 것이 앞선 것을 덮어쓴다

발생한 문제는 자동 리뷰조차 발견하지 못한다. 리뷰하는 쪽이 받는 코드는 덮어쓴 뒤의 코드라서
보기에는 완전히 정상이기 때문이다.

**agentflow는 바로 이 세 공석을 메우기 위해 왔다.**

코드 짜는 AI를 하나 더 주는 것이 아니다. 당신에게 **제도** 를 준다:
AI가 짠 코드는 반드시 다른 AI들의 리뷰와 검수를 통과한 뒤에야 당신의 손에 닿는다.

<a id="quickstart"></a>
## 🗣️ 당신은 한 마디만 하면 된다

```
/wf 잠금 정책을 지원하는 로그인 기능을 만들고 싶어요
```

**그다음부터 당신의 일은 없다.**

```
요구사항 분해 →  설계   →  태스크  →  병렬      →  3단계     →  자동 수정  →  납품
                          분할      코딩        리뷰
   AI         3개의 AI    AI      여러 AI      3개의 AI     AI          ✅
```

- 🤖 **3개의 AI가 각각 기술 안을 내고**, 오케스트레이터 AI가 가로로 비교한 뒤 선택
- ✂️ **충돌하지 않도록 파일 경계로 태스크를 분할**하고, 여러 AI가 동시에 착수
- 🚧 **3개의 게이트가 자동 리뷰**. 통과하지 못하면 새 AI를 파견해 고치고, 끝나면 처음부터 다시
- 🔁 **최대 3라운드**. 그래도 안 되면 멈추고 어디서 막혔는지 알려준다

한 마디에서 동작하는 코드까지, 그 사이에 당신이 한 번 끄덕일 필요도 없다.

**이것이 1인 회사의 바람직한 모습이다: 당신은 의사결정 지점에만 나타나고, 라인 위에는 서지 않는다.**

## 👥 당신의 인력 편성표

1인 회사는 「한 사람이 모든 일을 다 하는 것」이 아니라, **한 사람이 모든 자리를 관리하는 것** 이다.
agentflow가 연구개발 부서의 편제를 채워 준다:

| 자리 | 하는 이 | 당신이 할 일 |
|---|---|---|
| 📋 프로덕트 매니저 | AI가 요구사항을 묻고, 검사 가능한 검수 목록으로 작성 | 질문에 답하기 |
| 🏗️ 아키텍트 | 3개의 AI가 각각 안을 내고, 오케스트레이터가 가로로 비교해 선택 | — |
| 📊 프로젝트 매니저 | AI가 파일 경계로 태스크를 나누고 충돌 여부 검사 | — |
| 👨‍💻 엔지니어 ×N | 여러 AI가 병렬로 작업 | — |
| ⚙️ CI / 빌드 | 스크립트가 타입 체크와 테스트를 실행, AI 토큰 불필요 | — |
| 🔍 코드 리뷰어 | 다른 AI가 리뷰, 보기만 가능하고 변경 불가 | — |
| 🧑‍💼 QA / 검수 | 코드를 본 적 없는 AI가 진짜 사용자처럼 한 번 써 보기 | — |
| 📚 지식 관리 | AI가 이번 라운드에서 밟은 함정을 교훈으로 기록, 다음 라운드에 자동 탑재 | 뭘 기록할지 확인 |
| 👑 **CEO** | **당신** | **뭘 원하는지 말하고, 결정하고, 책임진다** |

**아홉 자리, 여덟은 AI가 한다.**

<a id="gates"></a>
## 🚧 3개의 자동 리뷰 게이트

```
게이트 1  AI 토큰이 들지 않는 검사
          타입 체크와 테스트를 실행. 가장 싸므로 맨 앞에 둔다 — 빨리 실패해서 비용 절약
             ↓ 통과
게이트 2  AI가 코드를 리뷰
          다른 AI가 리뷰. 리뷰 전에 스냅샷을 저장하고, 끝난 뒤 중간 바꿔치기가 없었는지 대조
          보기만 가능하고 변경 불가, 다른 누구를 재파견할 수도 없다
             ↓ 반드시 고쳐야 할 문제 없음
게이트 3  AI가 사용자로서 검수
          코드를 전혀 본 적 없는 AI가 진짜 사용자처럼 제품을 실제로 써 본다
             ↓ 전부 통과
          ✅ 납품
```

**게이트 3이 결정타다.** 🎯

코드도 테스트도 볼 수 없고, 어떻게 구현됐는지도 모른다.
손에 쥔 것은 「어떻게 되면 통과인가」라는 체크리스트와 실제로 돌아가는 프로그램뿐이다.

**그래서 진짜로 써 보는 수밖에 없다.**

앞의 두 게이트는 코드를 보지만, 「돌아가기는 하는데 쓰기 불편한」 류의 문제는 진짜 사용자가 되어 봐야만 부딪힌다.
1인 회사가 가장 겪기 쉬운 사고가 이것이다. 자기 제품에 너무 익숙해져서, 그게 얼마나 불편한지 이미 보이지 않게 된 것이다.

## 🎯 실제로 잡아낸 기록

이론이 아니다. 매 건에 리포트 파일이 증거로 있다.

| 게이트 | 잡아낸 것 |
|---|---|
| 🥇 **게이트 1** | **설정해 둔 검사 명령 자체가 고장 나 있었다.** 8개의 코딩 AI가 전부 못 봤다. 그들이 실행한 것은 개별 파일이고, 설정에는 디렉터리 전체가 쓰여 있었기 때문이다. |
| 🥈 **게이트 2** | **변조 방지 기능 자체가 고장 나 있었다.** 스냅샷 기능이 기록한 지문이 실제 파일과 맞지 않았다. 즉 이 보안 장치는 계속 헛돌고 있었던 것이다. |
| 🥈 **게이트 2** | **한 모듈이 6곳 망가졌는데 테스트는 한 곳도 에러를 내지 않았다.** 테스트 전부 초록. 코드만 봐서는 테스트가 아무것도 감시하고 있지 않다는 걸 알 수 없다. |
| 🥉 **게이트 3** | **쓰기 불편한 곳 9건, 그중 한 건은 진짜 계산 오류였다.** 폭락 중인 코인에서 랭킹 알고리즘이 깨져, 진짜 가치 있는 종목을 뒤로 밀어 버리고 있었다. |

**모든 게이트는, 그 게이트만이 잡을 수 있는 것을 잡았다.**

이 네 건 중 하나라도 프로덕션에 새어 나갔다면, 1인 회사에는 대신 받쳐 줄 두 번째 사람이 없다.

<a id="guards"></a>
## 🛡️ 무엇을 기계적으로 막는가

1인 회사에서 가장 비싼 비용은 **재작업** 이다. 다시 확인해 줄 사람이 없어서, 오류는 계속 하류로 굴러간다.

**그래서 AI에게 당부하는 방식에 기대지 않고, 스크립트로 하드 블록한다.** 아래는 전부 코드가 관할한다:

| 발생 가능한 문제 | 막는 방법 |
|---|---|
| 테스트 케이스를 하나도 돌리지 않았는데 명령이 성공 반환 | 명령 성공 **그리고** 출력에 지정된 문자열이 나타날 것을 요구 |
| 하나의 기준에 요구사항이 여럿인데 하나만 검사 | 요구사항마다 체크포인트 설정, 전부 맞아야 통과 |
| 요구사항 단계에서 기술 스택이 고정돼 버림 | 요구사항 문장에 언어·프레임워크 이름이 나오면 즉시 에러 |
| 판단의 전제조건을 적을 곳이 없음 | 사람이 판정하는 기준에는 「어떤 조건에서 비교가 유효한가」를 반드시 기재 |
| 같은 명령이 다른 터미널에서 결과가 뒤집힘 | 명령 내 중첩 따옴표는 즉시 에러 |
| 리뷰하는 동안 코드가 바뀜 | 리뷰 전 스냅샷 저장, 끝난 뒤 대조 |
| 리뷰할 코드가 의존성 디렉터리에 파묻힘 | 태스크 목록에 선언된 파일만 리뷰, 초과 변경은 별도로 나열 |
| 중단 후 어디까지 했는지 모름 | 스크립트가 현재 진행, 부족한 것, 지난번 중단 지점을 알려줌 |
| 중단이 주인 없는 스크린샷과 로그를 남김 | 어떤 리포트에도 인용되지 않은 파일을 지목해 나열 |
| 기록해야 할 진행이 기록되지 않음 | 기록과 디스크의 파일을 양방향으로 대조 |
| 검사 중에 몰래 규칙을 바꿈 | 시작할 때 규칙 지문을 저장하고, 이후 매번 대조 |
| 「나 혼자 문제 없다고 했다」가 무시됨 | 매번 결론을 누가 내렸는지 출력 |
| 오케스트레이터 AI가 플로우를 벗어나 제멋대로 행동 | 7종류의 액션은 반드시 먼저 당신에게 묻고, 기록이 없으면 위반 |

**13개의 기계적 가드, 단 하나도 「자율」에 기대지 않는다.**

한 사람의 회사에서는 **제도를 반드시 스크립트로 써야 한다** — 규칙으로만 써 두면, 바빠지면 아무도 지키지 않는다.

<a id="install"></a>
## 🚀 3분 만에 설치

```powershell
# 먼저 뭘 할 건지 확인 — 이 단계는 아무것도 바꾸지 않는다
powershell -ExecutionPolicy Bypass -File install.ps1

# 문제없으면 실제로 설치
powershell -ExecutionPolicy Bypass -File install.ps1 -Apply -EnableAgentTeams

# 프로젝트 디렉터리에서 초기화
cd D:\your\project
powershell -ExecutionPolicy Bypass -File <agentflow>\scripts\init-workflow.ps1
```

설치 후 Claude Code를 재시작하고 `/wf` 를 입력해 시작.

**Windows에서 동작. tmux도 WSL도, 추가 CLI 도구도 필요 없다.** 💻

초기화 스크립트는 인크리멘털하며, 기존 파일을 덮어쓰지 않는다. 프로젝트가 무슨 언어인지 자동으로 판별하고,
그에 맞는 검사 명령을 연결하고, `.gitignore` 를 만들고, 마지막으로 설정한 명령을 실제로 한 번 실행해 쓸 수 있는지 확인한다.

**빌릴 서버도, 가입할 계정도, 월정액도 없다. 설치하면 그건 당신 자신의 것이다.** 🆓

<a id="routes"></a>
## 🧭 7개의 루트 — 작은 태스크는 풀코스를 돌지 않는다

1인 회사의 토큰 비용은 자비다. 그래서 먼저 태스크가 얼마나 큰지 보고, 어떤 루트로 갈지 정한다:

| 루트 | 쓰는 때 |
|---|---|
| `direct` | 한두 줄 고치는 소소한 일, 바로 실행 |
| `guarded` | 중간 규모 변경, 리뷰 하나 추가 |
| `full` | 완전한 기능, 3개의 게이트 전부 통과 |
| `refactor-safe` | 기존 코드 리팩터링, 기본은 직렬 |
| `diagnose` | 문제 추적, 먼저 재현하고 그다음 수정 |
| `research-only` | 조사만, 코드는 쓰지 않음 |
| `review-only` | 코드 리뷰만 |

**모기 잡는 데 대포를 쓰지 않는다.** 🦟

<a id="design"></a>
## 🧠 핵심 설계

### 📋 검수 체크리스트가 전체 플로우의 출발점

인력 리뷰를 없애려면, **착수 전에 검수 기준이 기계로 판정 가능한 상태** 여야 한다는 것이 전제다.

- **기계 판정**: 먼저 「어떤 입력을 주고, 무엇을 기대하고, 무엇을 기준으로 같다고 할지」를 명확히 쓰고,
  기술 안이 정해지면 구체적인 명령으로 번역한다
- **AI 판정**: 「어느 화면에서 볼 것인가」 「어떤 전제조건에서 비교가 유효한가」 「무슨 증거를 돌려줄 것인가」를 반드시 명시한다

검사 방법을 설명할 수 없는 것은 검수 기준이 아니다. 소원일 뿐이다 — 스크립트가 바로 막아 낸다.

**이것이 1인 회사 모델 전체가 성립하는 기반석이다.**
코드를 한 줄씩 읽을 수는 없다. 당신이 읽을 수 있는 것은 결론뿐 — 그러니 그 결론은 반드시 신뢰할 수 있는 것이어야 한다.

### 🧪 테스트만 통과해서는 인정할 수 없다

테스트 통과는 「코드와 테스트가 맞다」는 것만 설명할 뿐, 코드가 옳다는 것을 설명하지 않는다.

그래서 이것을 반드시 한다: **일부러 코드를 망가뜨려 보고, 테스트가 화를 내는지 본다.**
`>` 를 `>=` 로 바꾸고, 어떤 분기를 지우고, 상수에 1을 더한다 — 한 곳을 망가뜨리고 한 번 실행한 뒤 되돌린다.
테스트가 화를 내지 않았다면, 그 부분은 원래부터 테스트가 관할하지 못한 곳이다.

실제 측정 비교 — 같은 리포지터리, 같은 리뷰 라운드:

```
한 모듈: 6곳을 망가뜨렸더니 테스트가 6곳을 잡아냄
다른 모듈: 6곳을 망가뜨렸는데 테스트는 한 곳도 잡지 못함
```

유일한 차이: 앞쪽 모듈의 태스크 카드에는 「이걸 해야 한다」고 쓰여 있었고, 뒤쪽에는 없었다.

### 📂 같은 배치의 태스크는 같은 파일을 건드릴 수 없다

두 AI가 같은 파일을 동시에 고치고, 나중 것이 앞선 것을 덮어쓴다 — 이런 문제는 자동 리뷰로는 보이지 않는다.

그래서 태스크는 기능이 아니라 **파일** 로 나눈다. 같은 배치의 태스크의 파일 목록이 겹치는지
검사하는 스크립트가 있다.

## 🙋 당신이 나서야 할 때

1인 회사의 CEO가 가장 아껴야 할 것은 주의력이다. 전체 플로우에서 당신이 필요한 곳은 4군데뿐이다:

| 때 | 설명 |
|---|---|
| 1️⃣ 첫 단계의 요구사항 히어링 | 요구사항은 당신에게서만 올 수 있다, 생략 불가 |
| 2️⃣ 오케스트레이터 AI가 플로우 밖의 행동을 하려 할 때 | 돌고 있는 AI를 중간에 끊기, 플로우 규칙 바꾸기, 검사 건너뛰기 — 반드시 먼저 당신에게 묻는다 |
| 3️⃣ 마무리 때 뭘 기록할지 확인 | 저비용 확인. 응답이 없으면 자기 판단으로 기록 |
| 4️⃣ 3라운드가 지나도 미통과 | 비정상 상황. 정상적인 실행에서는 발생하지 않는다 |

**나머지 시간에는 당신만이 할 수 있는 일을 하면 된다 — 제품을 생각하고, 고객을 만나고, 돈을 받는다.** 💰

## ⚠️ 적용 범위

시간을 낭비하지 않도록, 못 쓰는 부분을 미리 밝힌다:

- 💻 **Windows 환경.** 검사 명령이 PowerShell 기반이다. Mac과 Linux에서는 완전히 돌지 않는다.
- 🖥️ **순수 코드베이스에서는 효과가 떨어진다.** 돌려볼 수 있는 화면이나 명령이 없으면 게이트 3이 평범한 통합 테스트로 퇴화한다.
- 💸 **AI 병렬 실행은 토큰이 약 5배 든다.** 간단한 CRUD는 AI 하나가 더 경제적이다 — 그래서 7개의 루트가 있다.
- 🧪 **Agent Teams는 Claude Code의 실험 기능**으로, Windows에서는 단일 윈도우 모드만 가능하다.
  쓸 수 없으면 자동으로 하나씩 순차 실행으로 디그레이드되며, 플로우는 끊기지 않는다.

## ⚙️ 코드를 수정할 때 주의

`scripts` 아래의 `.ps1` 파일은 반드시 **UTF-8 with BOM** 으로 저장해야 한다.

Windows PowerShell 5.1은 BOM이 없는 파일을 시스템 기본 인코딩으로 디코딩한다:
CJK 주석은 바로 깨진 글자가 되고, 이어서 따옴표 짝이 안 맞고, 스크립트 전체가 구문 에러로 죽는다.

VS Code로 수정한다면 오른쪽 아래 인코딩에서 "UTF-8 with BOM" 을 선택. 명령줄로 고치는 법:

```powershell
$enc = New-Object System.Text.UTF8Encoding($true)
Get-ChildItem .\scripts -Filter *.ps1 | ForEach-Object {
    $t = [IO.File]::ReadAllText($_.FullName, [Text.Encoding]::UTF8)
    [IO.File]::WriteAllText($_.FullName, $t, $enc)
}
```

**설정이 YAML이 아니라 JSON인 이유**: 검사 스크립트가 Windows PowerShell 5.1에서
아무것도 설치하지 않고 돌아가게 하기 위해서다. 5.1은 YAML을 읽지 못한다.
검사 스크립트가 도는가 안 도는가가 이 플로우의 자동화 가능 여부를 직접 결정한다.
