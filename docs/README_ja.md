## 🧩 ひとり会社に足りないのは「コードを書ける人」ではない

AI にコードを書かせるツールは、もう世の中に溢れている。ひとりでコードを書くこと自体は、とっくにボトルネックではなくなった。

**本当のボトルネックは、ひとりでいるとき、歯止めをかけてくれる人がいないこと。**

大企業では、1 行のコードが main ブランチに入るまでに、別のエンジニアのレビュー、QA のテスト、プロダクトの検収サインを通る。
ひとりで起業すると、この 3 つのポストはすべて空席——それなのに AI のコーディング速度は、あなたがひとりで埋め合わせられる速さをはるかに超えている。

だから、次の 3 つのことが必ず起きる：

### 🟢 テストは全緑、でも機能は偽物

AI はテストを通すために、偽データを入れ、フォールバック分岐を足し、アサーションを緩める。
テストは緑で、コードは壊れている。あなたは一面の緑を見て、全部順調だと思ってしまう。

### 🗯️ 「できました」に反論できる人がいない

検収基準がそもそも検査可能な形で書かれていないから。書いてあるのは「UX が良いこと」——
AI ができたと言ったら、何を根拠に「まだだ」と言える？ あなたはボスであり、唯一の検収者でもある。

### 📑 2 つの AI が同時に同じファイルを直し、後のものが前のものを上書きする

発生した問題は自動レビューにも発見できない——レビュー担当が受け取るのは上書き後のコードで、
見た目は完全に正常だから。

**agentflow は、この 3 つの空席を埋めるためにある。**

もうひとつコードを書く AI をあげるのではない。あなたに**制度**をあげる：
AI が書いたコードは、別の AI たちのレビューと検収を通ってからでなければ、あなたの手元に届かない。

<a id="quickstart"></a>
## 🗣️ あなたが言うのは一言だけ

```
/wf ロックアウトポリシー付きのログイン機能を作りたい
```

**そのあとは、あなたの出番はない。**

```
要件分解 →  設計    →  タスク  →  並列      →  3 段     →  自動修正 →  納品
                      分割      コーディング   レビュー
  AI       3 つの AI    AI      複数の AI     3 つの AI    AI         ✅
```

- 🤖 **3 つの AI がそれぞれ技術案を出し**、統括 AI が横比比較して採用を決める
- ✂️ **ファイル境界で衝突しないタスクに分割**し、複数の AI が同時に着手
- 🚧 **3 つのゲートが自動レビュー**。通らなければ新しい AI を派遣して修正し、終わったら最初から流れ直す
- 🔁 **最大 3 ラウンド**。それでも通らなければ止まって、どこで詰まっているかを教えてくれる

一言から動くコードまで、その間にあなたが一度も頷く必要はない。

**これこそがひとり会社のあるべき姿：あなたは意思決定ポイントにだけ現れ、ラインの上には立たない。**

## 👥 あなたの人員配置表〔オーグチャート〕

ひとり会社は「ひとりですべてをやる」ではなく、**ひとりですべてのポストを管理する**こと。
agentflow が開発部の定員を埋めてくれる：

| ポスト | やるのは誰 | あなたの仕事 |
|---|---|---|
| 📋 プロダクトマネージャー | AI が要件を尋ね、検査可能な検収リストに書き起こす | 質問に答える |
| 🏗️ アーキテクト | 3 つの AI がそれぞれ案を出し、統括が横比較して選択 | — |
| 📊 プロジェクトマネージャー | AI がファイル境界でタスクを切り、衝突がないか検査 | — |
| 👨‍💻 エンジニア ×N | 複数の AI が並列で作業 | — |
| ⚙️ CI / ビルド | スクリプトが型チェックとテストを実行、AI トークン不要 | — |
| 🔍 コードレビュアー | 別の AI がレビュー、見るだけで変更は不可 | — |
| 🧑‍💼 QA / 検収 | コードを見たことのない AI が、本物のユーザーとして使ってみる | — |
| 📚 ナレッジ管理 | AI がこのラウンドで踏んだ落とし穴を教訓として記録し、次回に自動で持ち越す | 何を記録するか確認 |
| 👑 **CEO** | **あなた** | **欲しいものを言い、決断し、責任を負う** |

**9 つのポスト。8 つは AI が担当。**

<a id="gates"></a>
## 🚧 3 つの自動レビューゲート

```
ゲート 1  AI トークンを使わないチェック
          型チェックとテストを実行。いちばん安いので最初に置く——早く失敗してコスト節約
             ↓ 通過
ゲート 2  AI がコードをレビュー
          別の AI がレビュー。レビュー前にスナップショットを保存し、後で途中改変がないか照合
          見るだけで変更は不可。誰かに再派遣することもできない
             ↓ 必須修正の問題なし
ゲート 3  AI がユーザーとして検収
          コードを一切見たことのない AI が、本物のユーザーのように製品を実際に使ってみる
             ↓ すべて通過
          ✅ 納品
```

**ゲート 3 が切り札。** 🎯

コードもテストも見られず、実装方法も知らない。
手元にあるのは「どうなれば合格か」のチェックリストと、実際に動くプログラムだけ。

**だから、実際に使ってみる以外に方法がない。**

最初の 2 つはコードを見るが、「動くが使いにくい」系の問題は、本当にユーザーになりきらないと見つからない。
ひとり会社が最もハマりやすい事故がこれ——自分の製品に慣れすぎて、どれほど使いにくいかがもう見えていない。

---

## 🎯 実際に捕まえた実績

理論ではない。すべてレポートファイルが証拠として残っている。

| ゲート | 捕まえたもの |
|---|---|
| 🥇 **ゲート 1** | **設定されたチェックコマンド自体が壊れていた。** 8 つのコーディング AI が誰も気づかなかった——彼らが実行していたのは個別のファイルで、設定にはディレクトリ全体が書かれていたから。 |
| 🥈 **ゲート 2** | **改ざん防止機能そのものが壊れていた。** スナップショット機能が記録していたフィンガープリントが、実際のファイルと一致しなかった。つまりこのセキュリティ機構はずっと空回りしていた。 |
| 🥈 **ゲート 2** | **あるモジュールを 6 か所壊したのに、テストは 1 か所もエラーを出さなかった。** テスト全緑。コードを読むだけでは、テストが何も監視していないことに気づけない。 |
| 🥉 **ゲート 3** | **使い勝手の悪い箇所 9 件、そのうち 1 件は本物の計算ミスだった。** 暴落しているコインでランキングアルゴリズムが破綻し、本当に価値のある候補を後ろに押しやっていた。 |

**どのゲートも、それにしか捕まえられないものを捕まえた。**

この 4 件のどれかひとつでも本番に漏れていたら、ひとり会社には代わりに守ってくれる 2 人目がいない。

<a id="guards"></a>
## 🛡️ 何を機械的にブロックするのか

ひとり会社でいちばん高いコストは**手戻り**——見直してくれる人がいないので、ミスはそのまま下流へ転がっていく。

**だから、AI への言い聞かせには頼らず、スクリプトでハードブロックする。** 下記はすべてコードが管轄している：

| 起こりうる問題 | ブロック方法 |
|---|---|
| テストケースが 1 件も実行されなかったのにコマンドが成功を返す | コマンドの成功**かつ**出力に指定文字列が現れることを要求 |
| 1 つの基準に要件が複数あるのに 1 つしか検査していない | 要件ごとにチェックポイントを設定、全ヒットで合格 |
| 要件段階で技術スタックが固定されてしまう | 要件文に言語名・フレームワーク名が現れたら即エラー |
| 判断の前提条件を書く場所がない | 人間が判断する基準には「どんな条件の下で比較が有効か」の記入を必須化 |
| 同じコマンドが別ターミナルで逆の結果になる | コマンド内の入れ子クオートは即エラー |
| レビュー中にコードが改変される | レビュー前にスナップショット、後で照合 |
| レビュー対象のコードが依存ディレクトリに埋もれる | タスクリストで宣言されたファイルのみレビュー、余分な変更は別途リスト |
| 中断後にどこまで進んだか分からなくなる | 現在の進捗・不足物・前回の中断位置をスクリプトが報告 |
| 中断が身元不明のスクショやログを残す | どのレポートにも引用されていないファイルを名指しでリスト |
| 記録されるべき進捗が記録されていない | 記録とディスク上のファイルの双方向照合 |
| チェック中にこっそりルールが変えられる | 開始時にルールのフィンガープリントを保存し、以後毎回照合 |
| 「私ひとりが問題ないと言っただけ」が無視される | 毎回「誰が結論を下したか」を表示 |
| 統括 AI がフローを飛び出して独断する | 7 類のアクションは必ず事前確認、記録がなければ違反 |

**13 の機械的ガード。ひとつとして「自主性」には頼らない。**

ひとりの会社では、**制度はスクリプトとして書かなければならない**——ルールとして書くだけでは、忙しくなれば誰も守らない。

<a id="install"></a>
## 🚀 3 分でインストール

```powershell
# まず何をするつもりか確認——このステップは何も変更しない
powershell -ExecutionPolicy Bypass -File install.ps1

# 問題なければ本インストール
powershell -ExecutionPolicy Bypass -File install.ps1 -Apply -EnableAgentTeams

# プロジェクトディレクトリ内で初期化
cd D:\your\project
powershell -ExecutionPolicy Bypass -File <agentflow>\scripts\init-workflow.ps1
```

インストール後に Claude Code を再起動し、`/wf` と入力して開始。

**Windows 上で動作。tmux も WSL も、追加の CLI ツールも不要。** 💻

初期化スクリプトはインクリメンタルで、既存のファイルは上書きしない。プロジェクトの言語を自動判定し、
対応するチェックコマンドを配線し、`.gitignore` を作り、最後に設定したコマンドを実際に一度実行して動作確認する。

**借りるサーバーも、登録するアカウントも、月額料金もない。インストールしたら、それはあなた自身のもの。** 🆓

<a id="routes"></a>
## 🧭 7 つのルート、小さなタスクはフルコースを通らない

ひとり会社のトークン代は自腹。だからまずタスクの大きさを見てから、どのルートを通るか決める：

| ルート | 使いどき |
|---|---|
| `direct` | 数行の小変更、そのまま実行 |
| `guarded` | 中規模の変更、レビューを 1 つ追加 |
| `full` | 完全な機能、3 ゲート全部通し |
| `refactor-safe` | 既存コードのリファクタリング、デフォルトは直列 |
| `diagnose` | トラブルシューティング、まず再現してから修正 |
| `research-only` | 調査のみ、コードは書かない |
| `review-only` | コードレビューのみ |

**蚊に大砲は使わない。** 🦟

<a id="design"></a>
## 🧠 コア設計

### 📋 検収チェックリストが全フローの起点

人力レビューをなくすには、**着工前に検収基準が機械で判定可能になっている**ことが前提となる。

- **機械で判定**：まず「どんな入力で、何を期待し、何をもって等しいとするか」を明確に書き、
  技術案が決まってから具体的なコマンドに翻訳する
- **AI が判定**：「どの画面を見るか」「どんな前提条件で比較が有効か」「どんな証拠を返すか」を必ず明記する

検査方法を説明できないものは検収基準ではない。ただの願いごと——スクリプトがその場で弾く。

**これが、ひとり会社モデル全体が成立するための礎である。**
コードを一行ずつ読むことはできない。あなたが読めるのは結論だけ——だからその結論は信頼できるものでなければならない。

### 🧪 テストが通っただけではダメ

テストの通過は「コードとテストが一致している」ことを示すだけで、コードが正しいことを示さない。

だから、これを必ずやる：**わざとコードを壊して、テストが怒るかを見る。**
`>` を `>=` に変え、ある分岐を消し、定数に 1 を足す——1 か所壊して 1 回実行し、それから戻す。
テストが怒らなかったら、その箇所はもともとテストの監視範囲外だったということ。

実測の比較——同じリポジトリ、同じレビューラウンド：

```
あるモジュール：6 か所壊して、テストが 6 か所検出
別のモジュール：6 か所壊して、テストは 1 か所も検出せず
```

唯一の違い：前者のタスクカードには「これをやること」と書かれていたが、後者には書かれていなかった。

### 📂 同じバッチのタスクは同じファイルに触れてはならない

2 つの AI が同時に同じファイルを直し、後のものが前のものを上書きする——こういう問題は自動レビューでは見えない。

だからタスクは機能ではなく**ファイル**で切る。同じバッチのタスクのファイルリストに重複がないかを
検査するスクリプトがある。

## 🙋 あなたが出る必要のある場面

ひとり会社の CEO が最も節約すべきは注意力。全フローの中であなたが必要なのは 4 か所だけ：

| 場面 | 説明 |
|---|---|
| 1️⃣ ステップ 1 の要件ヒアリング | 要件はあなたからしか来ない、省けない |
| 2️⃣ 統括 AI がフロー外の行動を取りたがる | 動いている AI の途中停止、フローのルール変更、チェックのスキップ——必ず先にあなたに聞く |
| 3️⃣ 終了時の「どの教訓を記録するか」の確認 | 低コストの確認。返事がなければ自分の判断で記録する |
| 4️⃣ 3 ラウンド経っても未通過 | 異常事態。正常な実行では発生しない |

**残りの時間は、あなたにしかできないことをやればいい——プロダクトを考え、顧客に会い、お金を回収する。** 💰

<a id="boundary"></a>
## ⚠️ 適用範囲

時間を無駄にしないよう、先に悪い話をしておく：

- 💻 **Windows 環境。** チェックコマンドは PowerShell ベース。Mac や Linux では完全には動かない。
- 🖥️ **純粋なコードベースでは効果が目減りする。** 動かせる画面やコマンドがなければ、ゲート 3 は普通の結合テストに退化する。
- 💸 **AI の並列実行はトークンが約 5 倍。** 単純な CRUD なら AI 1 台のほうが安い——だから 7 つのルートがある。
- 🧪 **Agent Teams は Claude Code の実験的機能**。Windows では単一ウィンドウモードのみ。
  使えない場合は自動的に逐次実行へ降格し、フローは止まらない。

## ⚙️ コードをいじるときの注意

`scripts` 配下の `.ps1` ファイルは必ず **UTF-8 with BOM** で保存すること。

Windows PowerShell 5.1 は BOM なしのファイルをシステム標準のコードページでデコードする：
CJK のコメントは文字化けし、クオートが対をなさなくなり、スクリプト全体が文法エラーで死ぬ。

VS Code で編集するなら、右下のエンコーディングで「UTF-8 with BOM」を選択。コマンドラインで直す場合：

```powershell
$enc = New-Object System.Text.UTF8Encoding($true)
Get-ChildItem .\scripts -Filter *.ps1 | ForEach-Object {
    $t = [IO.File]::ReadAllText($_.FullName, [Text.Encoding]::UTF8)
    [IO.File]::WriteAllText($_.FullName, $t, $enc)
}
```

**設定が YAML ではなく JSON な理由**：チェックスクリプトを Windows PowerShell 5.1 で
何もインストールせずに動かすため。5.1 は YAML を読めない。
チェックスクリプトが動くかどうかが、このフローを自動化できるかどうかを直接決める。
