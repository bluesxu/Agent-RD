# agentflow

给 Claude Code 用的一套开发流程。你只负责把需求说清楚，剩下的写代码、审代码、验收，都交给 AI 去做。

跑在 Windows 上，不需要装 tmux、WSL 或别的命令行工具。

搜索关键词：Claude Code、AI 开发流程、多 agent 协作、自动验收、代码审查自动化、
acceptance criteria、multi-agent workflow、mutation testing、PowerShell。

---

## 它想解决什么

让 AI 写代码不难，难的是**判断它到底写完了没有**。

常见的三种情况：

**第一种，测试全绿但功能是假的。** AI 为了让测试通过，会加假数据、加兜底分支、
把断言改松。测试是绿的，代码是坏的，而审代码的人看到测试绿了，很难看出这份绿是装出来的。

**第二种，"我做完了"这句话没人能反驳。** 因为验收标准当初就没写成能检查的样子。
写的是"用户体验要好"，那谁都可以说做完了。

**第三种，两个 AI 同时改一个文件。** 后改的把先改的覆盖掉，产生的问题自动审查发现不了——
审查的人拿到的代码是覆盖之后的，看起来完全正常。

这套流程从头到尾都在解决一件事：**在开工之前，就把"怎么算做完了"定死。**

---

## 什么时候用，什么时候别用

适合：

- 新功能开发，模块边界比较清楚
- 涉及权限、数据库、并发这类出错代价高的改动
- 以后需要拿出证据说明"当初验过什么"的项目
- Windows 环境

不适合：

- 改一两行的小事（用它是浪费，里面有专门的轻量路线，但更简单的做法是别用）
- 需求还没想清楚的探索性尝试
- 只想省钱省时间的日常小任务
- Mac 和 Linux。检查命令里写死了 PowerShell，在这两个系统上跑不完整

它内置了七条路线，会先看任务多大再决定走哪条。小任务不会被拖进全套流程。

## 安装

```powershell
# 先看看它打算做什么，这一步不会改任何东西
powershell -ExecutionPolicy Bypass -File install.ps1

# 确认没问题再真装
powershell -ExecutionPolicy Bypass -File install.ps1 -Apply -EnableAgentTeams

# 到你的项目目录里初始化
cd D:\your\project
powershell -ExecutionPolicy Bypass -File <agentflow>\scripts\init-workflow.ps1
```

安装脚本默认只是演示，不实际动手；要覆盖已有文件会先备份。

初始化脚本是增量的，已经有的文件不会被覆盖。它会看你的项目是什么语言，
配上对应的检查命令，建一个 `.gitignore`，然后把配好的命令实际跑一遍，
确认它们真的能跑起来。

装完重启 Claude Code，输入 `/wf` 开始。

## 怎么用

```
/wf 我想做一个支持锁定策略的登录功能
```

然后是四步：

**第一步：把需求问清楚。** 这一步你要参与。AI 会连着问你一串问题：
出错了怎么办、边界值怎么算、谁有权限、老数据怎么办、这次不做什么、
以及最重要的——每一条要求，将来靠什么判断做没做到。

产出两份文件：一份给人看的需求说明，一份给机器用的验收清单。

这一步有条硬规矩：**每条验收标准都必须能被检查**。说不清楚怎么检查的，
不算验收标准，算许愿，会被脚本直接拦下来。

**第二步：定技术方案。** 全自动。同时派两三个 AI 各自独立出方案，
然后由主控 AI 比较、选一个。切成一个个互不冲突的小任务。

**第三步：写代码 + 三轮检查。** 全自动。按任务的先后顺序派 AI 去写，
写完过三道检查。没过就派新的 AI 去修，修完从第一道重新来。最多三轮，
三轮还过不了就停下来找你。

**第四步：收尾。** 挑出值得以后复用的经验记下来。

### 三道检查分别是什么

**第一道，不花 AI 额度的。** 就是跑类型检查、跑测试这些命令。
最便宜所以放最前面，早点失败早点省钱。

**第二道，换一个 AI 来审代码。** 审之前先把要审的代码存一份快照，
审完对一下有没有被人中途改过。审的这个 AI 只能看不能改，也不能再派别人。

**第三道，找一个完全没看过代码的 AI，让它像用户一样把东西用一遍。**

第三道是最重要的一道。它拿不到代码、拿不到测试、也不知道是怎么实现的，
手里只有"做成什么样算通过"这份清单和一个能跑起来的程序。**所以它只能真的去用一遍。**

这一道能抓到前两道结构上抓不到的问题——前两道看的是代码，
而"能跑但很难用"这类问题，只有真的当一次用户才会撞见。

## 几个关键的做法

### 验收清单是整套流程的起点

不要人工审核，前提就是**验收标准在开工前已经能被机器判断**。

每条标准分两种：

- **机器判的**：第一步先写清楚"给什么输入、期望什么输出、用什么标准算相等"，
  等技术方案定了，第二步再翻译成具体命令
- **人或 AI 判的**：必须写清楚"从哪个界面/接口去看"、"在什么前提下比对才算数"、
  "要交回什么证据"

为什么第一步不许直接写命令：因为命令里带着语言和工具（比如 `node --test` 就是 Node），
等于在讨论技术方案之前就把技术定了。实际跑的时候，三个出方案的 AI 里有两个
开口第一句就是"技术栈其实不用讨论，已经定死了"。

### 光有测试通过不算数，得验证测试本身有用

测试通过只说明"代码和测试对得上"，不说明代码是对的。测试写得敷衍，照样全绿。

所以要求做一件事：**故意把代码改坏，看测试会不会报错。**
把大于改成大于等于、把某个判断删掉、把常数加一，改一处跑一次，然后改回去。
测试没报错，说明这处改动测试根本管不着。

实际跑出来的对比很说明问题——同一个仓库、同一轮审查：

```
一个模块，改坏 6 处，测试抓到 6 处
另一个模块，改坏 6 处，测试一处都没抓到
```

唯一的差别是：前一个模块的任务书里写了"要做这件事"，后一个没写。

### 同一批任务不许改同一个文件

两个 AI 同时改一个文件，后面的把前面的覆盖掉，这种问题自动审查看不出来。

所以任务是按文件切的，不是按功能切的。有脚本检查同一批任务的文件清单有没有重叠。

## 它具体拦住了什么

这套东西的主张是"不靠嘱咐 AI，靠脚本硬拦"。下面每一条都是脚本在管：

| 会出什么问题 | 怎么拦 |
|---|---|
| 测试命令一个用例都没跑到，却返回成功 | 要求命令成功**并且**输出里出现指定的字样 |
| 一条标准有好几个要求，只检查了一个 | 有几个要求就配几个检查点，全中才算过 |
| 需求阶段就把技术栈定死了 | 需求阶段的文字里出现语言、框架名，直接报错 |
| 判断的前提条件没地方写 | 人工判定的标准必须填"在什么条件下比对才算数" |
| 同一条命令换个终端结果就反了 | 命令里带嵌套引号直接报错 |
| 审代码的时候代码被人改了 | 审之前存快照，审完对一下 |
| 要审的代码被依赖目录淹没 | 只审任务清单里声明过的文件，多改的单独列出来 |
| 被打断后不知道做到哪了 | 有脚本告诉你当前进度、缺什么、上次断在哪 |
| 中断留下一堆没人认领的截图日志 | 点名列出没被任何报告引用的文件 |
| 该记的进度没记 | 拿记录和硬盘上的文件对账，两个方向都查 |
| 检查过程中偷偷改规则 | 开工时把规则文件存个指纹，后面每次对比 |
| "只有我一个人说没问题"被忽略 | 每次检查都打印结论是谁下的，自己说的不算独立验证 |
| 主控 AI 跳出流程自作主张 | 七类动作必须先问你，问了要记，没记就算违规 |

## 实际跑出来的数据

先说清楚：下面每一行都能在硬盘上找到对应的文件。

早期还有另一个项目的数据（一个短链服务），**那个项目已经被删了，
数字再也没法核对**，所以全部去掉了，不作为证据用。

**项目：币安 4 小时均线选币的命令行工具**（7 条验收标准，TypeScript）

| 项目 | 数字 | 对应文件 |
|---|---|---|
| 验收标准 | 7 条（机器判 5 条，AI 判 2 条） | `acceptance.json` |
| 第一道检查 | 跑了 2 轮，测试从 29 个涨到 35 个 | `l1-round1.json`、`l1-round2.json` |
| 第二道检查 | 第一轮 3 个必须改的问题，第二轮清零 | `l2-round1.md`、`l2-round2.md` |
| 第三道检查 | 6 条通过，1 条卡住 | `l3-round1.md` |
| 经验沉淀 | 3 条 | `lessons/` |
| 真实运行 | 扫了 530 个币，8 秒跑完 | `evidence/ac-6-main-run.log` |

### 每道检查抓到了什么

**第一道**抓到：配好的检查命令本身是坏的。8 个写代码的 AI 全都没碰到，
因为它们跑的是具体文件，而配置里写的是整个目录。

**第二道**抓到：存快照那个功能记录的指纹，和实际文件对不上——
也就是说这个防篡改功能本身一直是坏的。只有真去核对的人才会发现。

**第二道**还抓到：一个模块改坏 6 处，测试一处都没报错。测试是全绿的，
光看代码看不出来测试根本没在管事。

**第三道**抓到：9 条用起来别扭的地方，其中一条是真的算错了——
排序算法在暴跌的币上会失效，把有价值的标的挤到后面去。

每一道都抓到了只有它能抓到的东西。

## 什么时候需要你出面

| 时候 | 说明 |
|---|---|
| 第一步问需求 | 常规。需求只能从你这来，省不掉 |
| 主控 AI 想跳出流程做事 | 比如中途掐掉一个正在干活的 AI、改流程规则、跳过某道检查。这些必须先问你 |
| 收尾时确认要记哪些经验 | 低成本确认，你不回应它就按自己的判断记 |
| 三轮还没过，停下来了 | 不正常的情况，正常跑不会触发 |

## 已知的问题，不藏

**Mac 和 Linux 上跑不完整。** 检查命令里写死了 PowerShell。这是结构性的，不是"可能有点问题"。

**"换一个 AI 来审"其实没做到。** 设计上要求写代码和审代码的 AI 来自不同厂家，
实际两次都是同一家的大号审小号。同一家的模型，不知道的东西大概率一起不知道。
现在的临时办法是同一个模型换五种不同的提问角度，**这是缓解不是解决**——
换问法换的是找问题的顺序，不是知识盲区。


**证据只来自一个项目。** 记下来的那些经验，绝大多数只有一次观察，没有第二次验证。

**纯代码库效果打折。** 没有能跑起来的界面或命令，第三道检查就退化成普通集成测试了。

**多个 AI 并行大约费 5 倍的额度。** 简单的增删改查用一个 AI 更划算。

**Agent Teams 是实验功能**，Windows 上只能用单窗口模式。用不了会自动降级成一个个来，
流程不会中断。

## 目录结构

```
agentflow/
├── README.md
├── install.ps1                  把流程装到 Claude Code 里
├── skills/                      七个流程文件
│   ├── wf/                      入口，判断任务大小选路线
│   ├── wf-spec/                 第一步 问需求
│   ├── wf-plan/                 第二步 定方案、切任务
│   ├── wf-build/                第三步 写代码 + 三道检查
│   ├── wf-review/               第二道检查
│   ├── wf-eval/                 第三道检查
│   └── wf-keep/                 第四步 记经验
├── templates/                   各种文件的模板
├── examples/lessons/            经验条目怎么写才算合格
└── scripts/
    ├── init-workflow.ps1        在项目里初始化
    ├── gate-l1.ps1              第一道检查
    ├── check-ac.ps1             防止"命令成功但什么都没测"
    ├── check-artifacts.ps1      查进度、查中断、查规则有没有被改
    ├── freeze-target.ps1        存快照 + 对比有没有被改
    └── validate-plan.ps1        检查验收清单和任务清单写得对不对
```

在你项目里生成的东西：

```
.workflow/
├── attention.md              每次开工先看，控制在 30 行内
├── gates.json                第一道检查要跑哪些命令
├── bin/check-ac.ps1          守卫脚本，跟着项目走
├── lessons/                  攒下来的经验
└── features/{功能名}/
    ├── dispatch.md           为什么选这条路线
    ├── spec.md               需求说明
    ├── spec-internal.md      内部记录（第三道检查的 AI 看不到）
    ├── acceptance.json       验收清单
    ├── design.md             技术方案
    ├── tasks.json            任务清单
    ├── run.json              运行记录
    ├── review-target.json    审查快照
    └── reports/              三道检查的报告和证据
```

这些文件**都应该提交到 git**。早期版本建议把运行记录和报告忽略掉，
理由是"这些是临时产物"，那个判断是错的——它们是证据。
外部审计对这套东西最重的一条批评就是"审查报告一份都不存在"，
把它们忽略掉等于把这个批评变成制度。

## 改代码要注意

`scripts` 目录下的 `.ps1` 文件必须存成 **UTF-8 with BOM**。

Windows PowerShell 5.1 读没有 BOM 的文件时，会按系统默认编码去解，
中文注释直接变乱码，接着引号配不上对，整个脚本报语法错误。

用 VS Code 改的话，右下角编码选 "UTF-8 with BOM"。命令行修：

```powershell
$enc = New-Object System.Text.UTF8Encoding($true)
Get-ChildItem .\scripts -Filter *.ps1 | ForEach-Object {
    $t = [IO.File]::ReadAllText($_.FullName, [Text.Encoding]::UTF8)
    [IO.File]::WriteAllText($_.FullName, $t, $enc)
}
```

`.md` 和 `.json` 不受影响。

**为什么配置用 JSON 不用 YAML**：因为要让检查脚本在 Windows PowerShell 5.1 上
不装任何东西就能跑，而 5.1 不支持读 YAML。检查脚本能不能跑，
直接决定这套流程能不能自动化。
