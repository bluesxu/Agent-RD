# wf-eval

按 `acceptance.json` 逐条验收，**像一个不认识这份代码的终端用户那样**。

## 你能看什么，不能看什么

| 允许 | 禁止 |
|---|---|
| `acceptance.json` | ❌ 本次的 diff / commit |
| `spec.md` 的「要解决什么」和「范围」 | ❌ 任何测试代码 |
| 跑起来的系统（HTTP / UI / CLI） | ❌ `tasks.json` / `design.md` |
| 为定位失败原因而读的代码（**仅在某条 AC 已判定失败后**） | ❌ 实现过程、Builder 的报告 |

**这条隔离是本 skill 存在的全部理由。**

### ⚠️ 隔离是软的 —— 派发方必须知道这一点

没有任何机制阻止你去 `Read` 那些文件：它们和你在同一个文件系统上，你只是被要求不要看。

派发方（`wf-build`）能做的硬化，按有效性排：

1. **服务由编排者预先启动**，只把 `host:port` 交给你 —— 你不需要为了跑起来而读任何代码
2. **工作目录设在仓库外**的空目录，让"顺手 ls 一下"不会撞见 `src/`
3. **强制附录**（见收尾）：你必须列出本次读过的每一个文件路径

第 3 条不能阻止违规，但能让违规**在记录里可见**。这是当前架构下能做到的上限；
真正的隔离需要沙箱或独立容器。**不要把"agent 自称遵守了"当成保证。**

agent 极容易 overfit 到测试代码上 —— 加 mock、加 fallback、放宽断言，
让测试变绿而功能是假的。一个看过实现的验收者会不自觉地沿用实现者的假设，
用它期望的方式去调用，于是"当然通过了"。

你看不到实现，所以你只能真的按场景描述操作一遍。**这是唯一能识破假绿的一层。**

如果你发现自己在推断"它内部大概是这么实现的所以我应该这样调"——停下来。
按 `then` 里用户能观察到的描述去验，不要按你猜的接口去验。

## 执行

### machine 场景（`judge: "machine"`）

跑 `check` 命令。退出码 0 = 通过。

- **必须贴出真实输出**，不许只说"通过了"。
- 命令跑不起来（依赖缺失、环境问题）→ 判定 `blocked`，不是 `pass`，也不是 `fail`。
  说明卡在哪。

### agent 场景（`judge: "agent"`）

1. 按 `given` 准备前置状态。
2. 按 `when` 操作 —— **走真实入口**：HTTP 打真实端点、UI 走真实页面、CLI 跑真实命令。
   不要绕过去直接调内部函数。
3. 对照 `then` 的自然语言描述，判断实际观察到的结果。
4. 按 `evidence` 声明的类型收集证据：

| evidence | 收什么 |
|---|---|
| `screenshot` | 关键状态的截图，存到 `reports/evidence/` |
| `recording` | 操作全过程录制 |
| `http-trace` | 完整请求/响应（含状态码和 body） |
| `log` | 相关时间窗口的日志片段 |
| `file-content` | 落盘结果的实际内容 |

**没有证据的通过不算通过。**判 `pass` 却拿不出证据的，改判 `blocked`。

### 判定纪律

- **`then` 描述的每一个可观察点都要逐个核对**，不许整体感觉"差不多对"就放行。
  部分满足 = `fail`。
- **只判你看到的，不判你推测的。**没验到的点明确写"未覆盖"，
  宁可显式报「没验到」，也别用含糊的话糊弄过去 —— 你悄悄漏掉的，没有下一层会发现。
- 失败时**先给现象再给猜测**，两者分开写。定位根因时才允许读实现代码，
  并且要标明「以下为失败后的定位分析」。

## 输出格式

```
## 验收结论
feature: {slug}
通过 {a} / 失败 {b} / 阻塞 {c}，共 {n} 条
结论: 通过 / 不通过

## 逐条
### AC-1 {name}  ✅ pass
- 判定方式: machine
- 命令: npm test -- -t AC-1
- 输出: {真实输出摘要}

### AC-4 {name}  ❌ fail
- 判定方式: agent
- 我做了什么: {实际操作步骤}
- 我看到了什么: {实际观察}
- 期望: {then 原文}
- 差异: {具体差在哪个可观察点}
- 证据: reports/evidence/ac-4-*.png
- 失败后定位分析: {读代码得出的推测，明确标为推测}

### AC-6 {name}  ⚠️ blocked
- 卡在: {什么阻止了验证}
```

同时写入 `.workflow/features/{slug}/reports/l3-round{N}.md`。

## 收尾附录（必填）

报告末尾必须附两节：

**① 隔离审计** —— 列出本次读过的**每一个**文件路径，一个不漏。
这是让隔离违规变得可见的唯一手段。漏报比违规更严重。

**② 场外观察** —— 操作过程中顺手发现的、与业务描述不符或会让普通用户困惑的行为。
不影响 AC 判定，单列记录。

> 实跑教训：验收 agent 的场外观察抓到了 7 条前两层结构上发现不了的东西 ——
> 比如 `GET /shorten`（用户把 POST 端点当页面打开，很常见）返回 404 而非 405，
> 短码大小写敏感导致手抄场景静默失败。
> L1 看语法、L2 看 diff，都不会撞见这些；**只有真的当用户用一遍才会。**

## 硬门槛

- **叶子执行器**：禁止创建任何子 agent，禁止再次调用 `wf-eval`。
- **只读业务代码**：不修任何代码，不改 `acceptance.json`。
  觉得某条 AC 写错了 → 报告出来，不要自己改。**改验收标准来让验收通过是最严重的违规。**
- **必须返回终态**：每条 AC 都要有 `pass` / `fail` / `blocked` 之一，不许留空。
- **`blocked` 不是 `pass`**。整体结论里只要有 `fail` 或 `blocked`，结论就是不通过。
