# rd-spec

把一句话需求变成两份东西：人读的 `spec.md`，和机器烧的 `acceptance.json`。

**这是整条流水线唯一需要人的地方。**后面的实现、审查、验收全自动，
它们能不能判断"做完了没有"，完全取决于这一步写出来的 `acceptance.json`。

## 开工

1. 读 `.rd/attention.md`（存在的话）。
2. 按需求关键词检索 `.rd/lessons/`，命中要报告来源路径。
3. 生成 slug（kebab-case，从需求核心词来），创建 `.rd/features/{slug}/`。

## 第一步：拷问

**你的默认动作是提问，不是写文档。**

连续追问直到用户主动喊停，或你已经能填满 interview-probes.md 里诊断出的每一类缺口。
一次问一个，问完等回答再问下一个 —— 不要一口气抛十个问题，那会得到十个敷衍的答案。

> 📎 **拷问开始时** → 读 `references/interview-probes.md`
> 不读会：退回固定问卷 —— 用户已经写清边界还要按表问一遍，这是流程被弃用的方式。
> 四透镜诊断、六类工程问题「先诊断缺了才问」、档位探针深度、组合检查都在那里。

**先诊断开场白缺什么（四个缺口透镜），再决定问什么。** 透镜命中了才问，没命中就跳过：
含糊的开场白可能触发三四个探针，而一个具体、框得很好的开场白可能一个都不触发。
这是 **agent 内部诊断，不是给用户看的清单** —— 不许把诊断表原样打印给用户。
产品维度探针在前，它决定还要不要往下问。

先读 `dispatch.md` 的复杂度档位，据此决定探针深度：S 只问三问、M 标准四透镜 + 六类诊断、
L/XL 加产品级追问。具体清单在 interview-probes.md。

> 📎 **命中「用户评估不了」触发信号** → 读 `references/blindspot-map.md`
> 不读会：对根本评估不了的用户硬问 —— 问题榨出来的是猜测，不是需求。
> 触发信号与「评估不了 ≠ 还没决定」的区分、决策地图格式都在那里

**退出拷问前，先做组合检查**：把用户到目前为止说过的话在脑子里合起来，
找出对话没探过的非显然后果，趁还在对话里问。这是退出拷问的前置条件
（细节与纪律在 interview-probes.md）。

提问纪律：
- 用具体场景和边界案例检验理解，不要问"你还有别的要求吗"这种空问题。
- 用户说"你决定"时，给出你的建议和理由，让他确认，**不要静默替他决定**。
- 已经从 `lessons/` 或现有代码里能查到的事实，自己去查，不要问用户。

## 第二步：确认门 + 写 spec.md 和 spec-internal.md —— **两份，别写成一份**

> 📎 **拷问退出后、写文件前（确认门）** → 读 `references/confirmation-gate.md`
> 不读会：跳过「我理解得对不对」的确认门直接写成品 ——
> 用户第一次看到整体在成品文档里，纠正成本已经高了。

**先走确认门，再写文件。** 内部三桶草稿（用户说的 / 我推断的 / 我排除的）→
对外四节（在做什么 / 关键取舍 / 不在范围内 / 需要你拍板的残留项）→ 用户确认。
触发条件按两个信号判：拷问中问过阻塞式问题 **或** 复杂度 ≥ M。
「我推断的」那一桶最关键 —— 那是 agent 下的赌注，最值得用户纠正。

### `spec.md` —— 需求本身。**验收层验收者会读它的全文**

```markdown
# {feature name}

## 要解决什么
{一段话，说清楚为什么要有这个能力，不是描述怎么实现}

## 范围
- 做：...
- 不做：...   ← 必须有，不许写"暂无"

## 关键约束
{性能、兼容、安全、依赖等硬约束，每条一行}

## 已确认的决策
{拷问过程中用户拍板的东西，连同被否掉的替代方案。结算标签（已结算/指令/无标签）
是编排者内部信息，不写进本文件 —— 验收层整读 spec.md，标签会拆掉对抗性视角的盲区。见 confirmation-gate.md}

<!-- RD-DONE stage=spec artifact=spec at={ISO8601} -->
```

**末行的 `RD-DONE` 是收尾标记，必须真的写在最后一步。**
`check-artifacts` 靠它区分「写完的 spec.md」和「被中断在半路的 spec.md」——
没有标记的一律按未完成处理，四个必填小节也会逐个查是不是真有内容（空壳不算数）。

「已确认的决策」在**编排者内部**按结算测试分类（已结算 / 指令 / 无标签），
已结算必须能说出被否掉的替代方案，说不出的降级成指令。
**标签不写进 spec.md**（验收层整读 spec.md，标签会拆掉对抗性视角的盲区）——
spec.md 只列决策事实与被否掉的替代方案。写法见 confirmation-gate.md。

### `spec-internal.md` —— 你的顾虑和打算。**验收层验收者禁读**

```markdown
# {feature name} —— 内部记录

> ⛔ 本文件对 验收层验收者不可见。理由见下。

## 未决风险
{知道但还没解决的，明确写出来，不要藏}

## 怎么确认算对了
{这东西最可能怎么静默出错？你打算靠什么抓住它？}

<!-- RD-DONE stage=spec artifact=spec-internal at={ISO8601} -->
```

## 第三步：写 acceptance.json —— 硬门槛在这里

从 `templates/acceptance.json` 起手。每条场景必须有 `judge`：

- `judge: "machine"` —— **必须**给出 `checkIntent`：说清**输入是什么、期望输出是什么、用什么判等**。
- `judge: "agent"` —— **必须**给出 `evidence`：验收 agent 要交回什么证据（`screenshot` / `recording` / `http-trace` / `log` / `file-content`）。

### ⛔ 这一步不许出现任何技术选型

**业务梳理只讨论业务。**`checkIntent` 里不许出现语言、框架、测试运行器、包管理器的名字
—— `node` / `npm` / `pytest` / `cargo` / `go test` / `jest` / `mocha` / `dotnet` 一个都不行。
`validate-plan -Stage spec` 会机械拦截。

**对照**：

```
❌ node --test --test-name-pattern=feat\sAC-1
   ——「用微波炉加热 3 分钟」。加热多久是业务，用微波炉是技术。

✅ 对一组写死的输入跑计算，逐个断言四个周期的输出与手工验算值一致（相对误差 < 1e-9），
   并且能区分「用均值作初值」和「用首个数据点作初值」这两种实现
   —— 这条对 Node / Python / Go / Rust 方案同样成立。
```

**硬门槛（不可绕过）：**

> 一条验收标准如果既说不清 `checkIntent`（输入 / 期望输出 / 判等方式），
> 也说不清楚 agent 该拿什么证据来判定，
> 那它不是验收标准，是愿望。**回去继续拷问，直到它能被判定。**

判定不了的东西，后面没有任何一层能拦住 agent 说"我做完了"。

### 什么该 machine，什么该 agent

- **能写成断言的一律 machine**：状态码、返回结构、数据库最终态、错误码、性能阈值。
- **需要"像用户一样操作一遍"的才 agent**：多步交互流程、视觉呈现、跨页面状态、
  依赖真实外部服务的路径。

### 防 overfit 的写法

`judge: "agent"` 的场景，`then` 必须用**自然语言描述用户观察到的结果**，
不要写成代码断言，也不要提任何实现细节（函数名、文件名、变量名）。

反例（不要这样写）：
```
"then": "loginHandler 返回 { code: 401 }"
```
正例：
```
"then": "页面停留在登录页，顶部出现红色提示「用户名或密码错误」，
        地址栏不变，且浏览器没有存下任何登录凭据"
```

## 第四步：校验并收尾

```bash
node <agent-rd>/scripts/validate-plan.js -Feature {slug} -Stage spec
```

校验不过就按报错修，**不要手动跳过**。

通过后输出：

```
✅ 阶段 0 完成 — .rd/features/{slug}/
   spec.md          {N} 项约束，{M} 项排除
   acceptance.json  {X} 条场景（machine {a} / agent {b}）
   📍 Next: 调用 rd-plan 进入技术选型
```

## 收尾标记与模型档位

**收尾**：`spec.md` / `spec-internal.md` 末行盖 `<!-- RD-DONE ... -->`；
`acceptance.json` 顶层加 `"_complete": true`。两者都是**写文件的最后一个动作**——
中断可能发生在任何时刻，标记写在最后，才谈得上「有标记 = 写完了」。

**档位**：本阶段**必须 opus 级**。只有 rd-build 里按 tasks.json 写代码的 agent
可以用 Sonnet 这种级别的模型。

## 硬门槛

- **不许替用户做产品决策**。真实取舍必须让用户拍板，不因对话历史推断同意。
- **不许写出无法判定的验收标准**。写不出判定方式就继续问，这是本 skill 的唯一失败模式。
- **`spec.md` 的"不做"一节不许为空**。没有边界的需求，agent 一定会越界。
- 不创建 `.rd/attention.md` 或 `lessons/` 条目 —— 那是 `rd-keep` 的事。
