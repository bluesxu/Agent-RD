# 确认门与结算测试

> 📎 从 `skills/rd-spec/SKILL.md` 抽出。**加载条件**：拷问退出后、写文件之前。
> 不读会：跳过「我理解得对不对」的确认门直接写成品 ——
> 用户第一次看到整体在成品文档里，纠正成本已经高了，而且 acceptance.json 已经写完了。

## 确认门 —— 写文件前，先让用户确认理解

现在是「拷问 → 直接写 spec.md + acceptance.json」。缺的这一步是：
**用户第一次看到整体应该是在一份他能表态的摘要里，而不是成品文档里。**

### 第一步：内部三桶草稿（不给用户看）

把拷问结果分成三桶：

| 桶 | 内容 |
|---|---|
| **用户说的** | 用户明确说过的，逐条可回溯 |
| **我推断的** | 用户没明说、但你从对话里推出来的 —— **这是最值得纠正的表面**，是 agent 下的赌注 |
| **我排除的** | 你判断不在范围内的，以及为什么 |

### 第二步：对外四节（给用户确认，最多四节）

从三桶里提炼一份「两个产品同事在写 PRD 前会互相确认的那种话」，最多四节：

1. 在做什么
2. 关键取舍
3. 不在范围内
4. 需要你拍板的残留项

**为什么不是全面审计式的形状**：细节多到用户根本没法真的表态时，确认就是橡皮图章。

### 第三步：用户确认

触发条件按**两个信号**判（只看一个会漏）：

- 拷问过程中**问过阻塞式问题** → 走完整确认；**或**
- 复杂度档位是 **Standard/Deep（M 及以上）** → 走完整确认

**都不满足才跳过。** 实跑教训：用户一次性把 20 多项范围全写在开场白里、
一个问题都不用问的情况，只拿到一句话的确认 —— 后来改成两个信号一起判才堵住。

### 和 spec-internal.md 的关系

三桶草稿是确认门的**输入**（先诊断再对外），spec-internal.md 是确认后**留给 L3 的盲区**。
两个文件各司其职：草稿不落盘，internal 落盘但 L3 禁读。

## 结算测试 ——「已确认的决策」怎么分类

spec.md 的「已确认的决策」按**它有没有经受过检验**分类，不是按用户听起来有多确信。

| 标签 | 判定 |
|---|---|
| **已结算** | 对话里摆出过取舍 / 替代方案 / 风险，用户是**看着这些**做的选择 |
| **指令** | 用户断言了一个没人检验过的选择（冷不丁一句「就用 X 做」）。**不算结算**，有且只有一次被挑战的机会 |
| **无标签** | 只是 agent 推断或提议、用户从没回应的 —— 普通输入，永远不加标签 |

三条硬规则：

- **agent 永远不许给自己未经检验的提议贴标签**，也不许把敷衍的「行吧」升级成「用户明确选择」。
- 一条已结算决策**必须能说出「被否掉的替代方案是什么」** —— 说不出来的降级成指令。
- 对「评估不了」的领域（用户不懂）用 Blindspot Pass 画决策地图（见 `references/blindspot-map.md`），
  不要把「评估不了」误判成「已结算」。

**传给下游的纪律**：

- 把已结算决策连同被否掉的替代方案一起传给 L2 / L3，避免重新调研。
- **不传这个决策的论证和理由**（决策作为事实是用来划范围的，论证会锚定他们）。
- **结算标签（已结算 / 指令 / 无标签）是编排者内部信息，不许写进 `spec.md`。**
  L3 会整读 `spec.md` 全文，标签跟着决策事实送达 L3，盲区在构造上就不成立。
  所以 `spec.md` 的「已确认的决策」只列决策事实与被否掉的替代方案，**不列标签**；
  标签留在编排者的工作状态里（或 `spec-internal.md`，L3 禁读）。
- **任何对抗性 / 验证性的视角必须对「已结算」标记保持盲区** ——
  审查者如果知道「这是老板拍过板的」，他就不会真的去挑战它了。
