# rd-spec 的设计理由

> 📎 本文件 **role=human** —— 运行期永不加载，只给人看。
> 不读会：无运行期后果。

这里收集从 `skills/rd-spec/SKILL.md` 搬出来的说服性文字。agent 执行时不需要被说服。

## 为什么 spec 和 spec-internal 必须分成两份

L3 验收者除了逐条验收，还要写一节**场外观察** ——
按普通用户的习惯去用，顺手撞见的怪事。**那一节的价值全在于「它是自己找到的」。**

而「未决风险」和「怎么确认算对了」这两节，本质上是**一份提示清单**：
它们直接告诉验收者「作者怕哪里错、打算怎么抓」。
验收者照着清单找到了，**什么都不证明**。

> 同一条道理在 `rd-eval` 里也写着：「⛔ 这里不举例。列出往期 evaluator 找到过什么，
> 会让下一个带着答案去找。」——那是防框架泄漏，这里是防需求文档泄漏，是同一件事。

**「关键约束」为什么留在 spec.md**：它是**规格**，不是提示。
一个测试者本来就该知道「这个值该怎么算、门槛是多少」——
实跑里验收者正是靠它才正确理解了输出里某一列的口径。禁它反而有害。

**为什么不用「只读某几节」的写法**：读文件的工具只能整读，
「只读两节」这条规则**根本无法被遵守** —— 实跑里验收者只能事后报备
「工具返回了整个文件，我实际看到了全部 75 行」。
**做不到的规则会腐蚀那些做得到的规则。**分成两份文件，规则才成立。

> 没有未决风险、也说不出「最可能怎么静默出错」时，`spec-internal.md` 可以不建。
> **但通常你说不出来只是因为还没想** —— 回去继续拷问。

## 为什么「不许出现技术选型」是硬的

技术选型是**阶段 1** 的事，而且阶段 1 会派 2~3 个 agent
（尽量不同厂商/不同模型）独立出方案再仲裁 —— 那套安排成本不低。
在阶段 0 写下一条 `node --test ...`，等于**在开会之前就把结论写在了纸上**。

> 实跑教训：三个论证 agent 里有两个，开口第一句就是
> 「技术栈其实不用论证，已经被钉死了」。它们看出来了，然后照常论证完 ——
> 整个阶段 1 的成本照付，产出的是一场走过场。

## 为什么拷问力度没降反而更狠

写一条 `node --test -t AC-1` 很容易蒙混过关 —— 它只证明你会写命令。
而说清「给定这组输入，输出必须等于这组值，误差 < 1e-9」逼你把**判据本身**想明白，
那才是这一步真正要做的事。**具体命令是阶段 1 的产物**：技术选定之后，
`rd-plan` 会把每条 `checkIntent` 具化成选定栈的 `check` 命令。
你在这里写下的不是占位符，是**它必须满足的规格**。

## 为什么防 overfit 要自然语言

agent 极容易 overfit 到固定测试代码上 —— 各种 mock 和 fallback，
功能装模作样就通过了。自然语言描述的是目标本身，更难被曲解。
`rd-eval` 拿到场景时看不到实现，它只能真的去跑一遍。
