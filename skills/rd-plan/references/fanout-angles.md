# 异构角度清单与派发对账

> 📎 从 `skills/rd-plan/SKILL.md` 抽出。**加载条件**：派方案 agent 之前。
> 不读会：三份提示词写成一模一样 —— 换了模型也只是换措辞，仲裁变成挑文笔。

## 角度示例（按项目实际改，别照抄）

```
plan-a  优先【最小改动】：尽量复用现有结构，代价是可能留下将就
plan-b  优先【长期可维护】：允许较大重构，代价是本次工作量
plan-c  优先【风险最低】：优先可回滚、可灰度、失败面最小，代价是可能不够优雅
```

## 为什么角度必须各不相同

异构的目的是拿到**多条真正不同的路**。
但「不继承主对话历史 + 同一份提示词」这个组合，实际是让三个 agent
在同一个起点、朝同一个方向、按同一套偏好搜索 —— 换了模型也只是换个措辞。
三份高度雷同的方案会让仲裁变成挑文笔，而「被排除的方案」一节里
就真的写不出有分量的东西。

⚠️ 反过来也要小心：角度是**搜索方向**，不是**结论**。
不许在提示词里塞进倾向性判断（「我们倾向用 X」「Y 方案不太行」）——
那不叫差异化，那叫污染，和「不继承主对话历史」这条要求是同一个理由。

**每个 agent 的角度要写进 `planFanout.dispatched[].angle`**，
一句话，互不相同。`validate-plan` 会机械校验：缺角度、或者三份角度雷同，都不放行。

## planFanout 是派发那一刻钉死的名单

派发时写 `planFanout`（含 `at` / `dispatched[]`，每项 `name` / `model` / `angle` / `reportPath`）。
**`planFanout` 不许清、不许改** —— 改它等于篡改「本该有几份」。

对账在任何时刻成立：`inflight` 收齐后会被清空（那是它的正确行为），
但只要它被清空，「本该有三份」这个事实就跟着消失了 ——
派 3 回 2，清掉 inflight，「≥2 份完整方案」这条正好过线，少掉的那一份从此无人知晓。
`planFanout` 不被清，所以 `check-artifacts` 能永远对出这笔账。
