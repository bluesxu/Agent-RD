# 仲裁细则

> 📎 从 `skills/rd-plan/SKILL.md` 抽出。**加载条件**：方案收齐之后、开始仲裁时。
> 不读会：把方案的每一行重读一遍（买的是压缩却当场退光），
> 或在方案不足时悄悄降级而不留痕。

## 点数 —— 派出去几个，回来几个（先于仲裁）

```bash
node <agent-rd>/scripts/check-artifacts.js -Feature {slug} -Json
```

看 `proposalsComplete` 与 `proposalsLost`。**对不上就不许开始仲裁**，按顺序处理：

1. **先重派一次**。丢失的那一份用同样的任务书重新派，输出到同一个路径。
2. 重派仍然失败，才允许降级用剩下的继续 —— 但必须在 `design.md`
   的「未决风险」里明写：**少了哪一份、为什么少、这次仲裁只基于 N 份**。
3. 不足 2 份完整方案时**不许往下走**。只有一个方案，「被排除的方案」一节写不出来，
   整个并行论证等于走过场。

> 现在的问题从来不是「降级」本身 —— 3 份变 2 份有时确实只能接受。
> 问题是**降级得悄无声息**：三份的钱花了，两份的信息拿了，还以为是三份。

## 打分与复核

- 逐条对照 `spec.md` 的「关键约束」和 `acceptance.json` 打分裁决。
- 复核方案里的事实**顺着它给的 `file:line` 抽查**，不要把它读过的代码重读一遍 ——
  那样这次派发就白费了，你买的是压缩。
- 方案之间有实质分歧时，**分歧本身要写进 `design.md`**，不要只留胜出的那个。
  三个月后回来看，你需要知道当时为什么没选另一条路。
- 选型结论要能落到 `.rd/lessons/` 的候选 —— 但不要现在写，那是 `rd-keep` 的事。

## 仲裁者不许降档

仲裁是判断，不是记录。用低于 opus 级的模型仲裁，等于让最弱的环节决定最强的输入。
