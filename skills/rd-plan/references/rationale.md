# rd-plan 的设计理由

> 📎 本文件 **role=human** —— 运行期永不加载，只给人看。
> 不读会：无运行期后果。

## 为什么 spec-internal 给方案 agent、却不给 L3 验收者

它装的是「未决风险」和「打算怎么抓错」。
对**出方案**的人，这是必须知道的输入 —— 方案得能应对那些风险。
对**验收**的人，这是一份提示清单 —— 照着找到了什么都不证明。
同一份内容，对不同角色一个是必需、一个是污染。

## 为什么方案必须落盘（不只是说回来）

早先的要求是「agent 把方案说回来」，方案的唯一存在形式是那条返回消息。
实跑中派了 3 个，B、C 正常返回，**A 被中断后内容完全丢失，也没有任何重试** ——
最后拿 2 份做的仲裁，而且当时并不知道自己少了一份。
消息没回来 = 零，磁盘上连半截产物都没有，`check-artifacts` 再怎么查也查不出
一个从未存在过的东西。落盘之后，「回来几份」才变成可数的。

## 为什么需要两份看起来一样的名单（inflight + planFanout）

`inflight` 收齐后会被清空 —— 那是它的正确行为。
但只要它被清空，「本该有三份」这个事实就跟着消失了：
派 3 回 2，清掉 inflight，「≥2 份完整方案」这条正好过线，
少掉的那一份从此无人知晓。`planFanout` 是派发那一刻钉死的名单，
清 inflight 不影响它，所以对账在任何时刻都成立。

## 为什么 checkIntent 具化这一步存在

早期版本在阶段 0 就要求写一条可执行命令，
而命令必然带着语言和工具 —— 于是技术选型在你开始论证之前就已经定了。
实跑里三个论证 agent 有两个开口第一句就是「技术栈其实不用论证，已被钉死」。
「2~3 个异构 agent 独立出方案再仲裁」的安排成本不低，**别让它变成走过场**。

## 为什么方案阶段不能省算力

**方案错误没有任何下游守卫能捕获。**
L1/L2/L3 检查的全是「实现有没有对上方案」，没有一道门会问「这方案本身值不值得实现」。
方案错了，三道门会齐刷刷放行一个做得很漂亮的错东西。
实现阶段不一样 —— 任务书已把文件、步骤、验证命令写死，写错有三层门等着，
所以算力要省就省在那边。
