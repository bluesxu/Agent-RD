# wf

**你是分诊器。**先判断这件事有多大、多险，再选一条相称的策略。

> **为什么要分诊**：实测数据显示，全套流程一条验收标准约烧 **14 万 token**。
> 对一个改三行的 bug 走全套，成本是收益的几十倍。
> 反过来，对一个跨模块的新功能走轻量路径，会漏掉只有第三层门才抓得到的假绿。
> **策略必须与任务相称。**

## Phase 0 逃生舱

先检查用户是否明确表示要跳过流程：

- 命中「直接做 / just do it / 不用分析 / 别走流程 / 小修一下」→ 直接干，跳到 Phase 3 用 `direct` 策略
- 以「审一下 / review」开头 → 直接用 `review-only`
- 以「调研 / 查一下 / 方案对比」开头 → 直接用 `research-only`

**⛔ 不许自己发明逃生舱。**只有上面列出的短语算数。

## Phase 1 判断

### 1.1 先看项目，再下判断 [不可跳过]

**先行动，再判断。**不许凭需求描述猜复杂度。必须执行：

1. `git status` —— 当前改动状态
2. 读项目配置文件（`package.json` / `go.mod` / `pyproject.toml` / `Cargo.toml`，取存在的第一个）
3. 看一眼目录结构与规模
4. 读 `.workflow/attention.md`（存在的话）

### 1.2 任务类型

| 类型 | 信号 |
|---|---|
| **feature** | 新增、实现、加一个、做一个、支持…… |
| **bugfix** | 报错、修复、坏了、失败、500、崩溃、不对…… |
| **refactor** | 重构、整理、抽出来、改造、清理、行为不变…… |
| **chore** | 升级依赖、改配置、格式化、加脚本…… |
| **research** | 调研、对比、选型、怎么做、评估…… |
| **review** | 审查、看看代码、检查一下…… |

动词决定类型。多个匹配时选最核心的那个。

### 1.3 复杂度

| 级别 | 判定 |
|---|---|
| **S** | 单文件，范围清晰，预估 < 30 行 |
| **M** | 2~5 文件，单模块内，路径明确 |
| **L** | 5+ 文件，跨模块，需要规划 |
| **XL** | 架构级，API / schema 变动，多模块协作 |

**不确定时默认选高一级。**

### 1.4 风险

| 级别 | 判定 |
|---|---|
| **low** | 无生产影响，可逆，有测试覆盖 |
| **medium** | 修改现有行为，需要验证 |
| **high** | 权限/安全/隐私、持久化数据或迁移、并发或一致性语义、不可恢复的副作用、破坏对外契约 |

### 1.5 是不是在改已有代码

**单独判断这一条，它决定并行方式。**

- **绿地**：主要是新增文件 → 可以并行
- **存量**：主要是修改已有文件 → **并行经常不可用**

> 实测：在存量代码上做一次小重构，三个独立方案**一致认为核心部分切不开** ——
> 有几个文件必须一起改，谁先谁后都会留下一个「项目是坏的」中间态。
> **文件不重叠 ≠ 可并行。**存量改造的默认假设是串行。

## Phase 2 选策略

```
📋 分诊
  类型: {type}   复杂度: {S/M/L/XL}   风险: {level}   代码: {绿地/存量}
  策略: {strategy} — {一句话理由}
  预算量级: {见策略表}
  📍 Next: 加载策略并执行
```

### 决策矩阵

| 类型 \ 复杂度 | S | M | L / XL |
|---|---|---|---|
| **feature** | `direct` | `guarded` | `full` |
| **bugfix** | `direct` | `diagnose` | `diagnose` |
| **refactor** | `direct` | `refactor-safe` | `refactor-safe` |
| **chore** | `direct` | `direct` | `guarded` |
| **research** | `research-only` | `research-only` | `research-only` |
| **review** | `review-only` | `review-only` | `review-only` |

### 风险修正（只升不降）

- **risk = high** 且策略不含 L2 异构审查 → **升一档**（`direct` → `guarded`，`guarded` → `full`）
- **存量代码 + L/XL** → 即使类型是 feature，也要按 `refactor-safe` 的并行约束办（串行核心 + 并行下游）
- 用户明确要求更重的流程 → 接受
- **用户要求更轻的流程 → 可以降，但要说清楚放弃了哪道门、放弃后什么抓不到**

### 策略一览

| 策略 | 拷问 | 论证 | 实现 | 门 | 预算量级 |
|---|---|---|---|---|---|
| `direct` | 无 | 无 | 你自己写 | L1 | ~1 万 |
| `guarded` | 精简 | 无 | 串行单 agent | L1 + L2 | ~10 万 |
| `full` | 完整 | 3 方案并行 | 并行多 agent | L1+L2+L3 | **~14 万 / 条 AC** |
| `refactor-safe` | 精简（重点问边界） | 1~3 方案 | **串行核心 + 并行下游** | L1+L2+L3（回归导向） | ~10~20 万 |
| `diagnose` | 只问复现条件 | 无 | 先复现再修 | L1 + L2 | ~5~15 万 |
| `research-only` | 无 | 多方案并行 | **不写代码** | 无 | ~5~10 万 |
| `review-only` | 无 | 无 | **不写代码** | L2 | ~5 万 |

预算是量级参考，不是保证。**超出量级 2 倍时停下来告诉用户。**

### 创建 feature 目录

复杂度 **≥ M** 且策略不是 `review-only` / `research-only` 时，先建 `.workflow/features/{slug}/`。

**复杂度 S → 不建目录，保持轻量。**普通任务零产物，证据是 diff 和测试输出。

## Phase 3 执行

读对应的策略文件：

```
Read("<agentflow>/skills/wf/strategies/{strategy}.md")
```

严格照它执行。策略文件里标了 `[required]` 的阶段不可跳过。

## 铁律

1. **不许在没看项目的情况下评估复杂度** —— Phase 1.1 不可跳过
2. **不许自己发明逃生舱**
3. **不确定复杂度时选高一级**
4. **策略只能升级，降级必须用户明说，且要讲清放弃了什么**
5. **不许对 S 级任务走全套** —— 这是纯浪费，也是这套东西最容易被弃用的原因
6. **不许对存量代码假设可以并行** —— 先确认能不能切，切不开就串行

## 体系速读

四层流水线，人只在**业务梳理**这一步出现：

```
wf-spec    业务梳理 ── 产出 spec.md + acceptance.json
           硬门槛：每条验收标准必须机器可判定
wf-plan    方案与选型 ── 产出 design.md + 文件级 DAG
wf-build   实现 + 三层自动审核闭环（无人）
           L1 机械门 → L2 异构审查 → L3 场景验收
wf-keep    只沉淀能长期复用的经验
```

**三层门各自能抓到别人抓不到的东西**（实测）：

- **L1** 抓命令与配置错误 —— 零 LLM 成本，永远先跑
- **L2** 抓意图偏离与跨模块交互 bug
- **L3** 抓「测试全绿但功能是假的」—— **唯一能识破假绿的一层**

轻量策略省掉的就是后面两道门。**省得对不对，取决于这次改动值不值得。**
