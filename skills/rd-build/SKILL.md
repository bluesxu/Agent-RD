# rd-build

按 DAG 并行实现，然后进入三层自动审核闭环。**正常路径全程无人**。

**前置**：`design.md` + `tasks.json` 存在且已通过 plan 阶段校验。

## 你的角色

**你是编排者，不是实现者。**产品代码由 Builder 写，审查由 reviewer 写，
验收由 evaluator 判。你只做：拆发、等待、读报告、决定下一轮。

例外：L1 失败后 10 行以内的机械修复（import 漏了、类型注解、格式），你可以直接改。
超过这个范围一律派 fix agent。

## 一、并行实现

### Step 1 选并行载体 —— 三档，不是两档

按顺序尝试，**用得上哪档就用哪档，不要跳级也不要预判失败**：

| 档 | 条件 | 说明 |
|---|---|---|
| **A. Agent Teams** | `TeamCreate` 工具存在 | 队友有共享任务列表、可互相通信 |
| **B. 并行子 agent** | 总是可用 | 同一条消息里派多个独立 agent，各有干净上下文。**没有共享任务列表、不能互相通信**，全靠你编排 |
| **C. 串行** | 前两档都不行 | 你自己按 layer 顺序实现 |

```
TeamCreate({ team_name: "{slug}-team", description: "AgentRD build" })
```

**`TeamCreate` 不存在或实际返回错误 → 降到 B，不是直接降到 C。**

> 这一档是实跑补上的。原设计只有 A 和 C 两档，而 `TeamCreate` 在很多环境下
> 根本不存在（Agent Teams 是实验性功能，要显式开启且需重启）。
> 直接降级串行会白白丢掉并行能力 —— 而 B 档不需要任何开关，永远可用。

B 档与 A 档的编排规则**完全相同**（同消息派发、文件白名单、立即等待、深度锁 1 层），
唯一区别是队友之间无法通信，所以**跨任务的协调必须全部经过你**。

降级时告知用户一句，然后继续，不要停下来问。

### Step 1b 模型档位 —— 这里是唯一可以省算力的地方

> **只有动代码的流程可以安排 Sonnet 这种级别的模型，其他部分都必须是 opus 级别的模型。**

| 角色 | 档位 |
|---|---|
| **Builder**（按 `tasks.json` 写代码） | **可以 Sonnet 级** |
| **fix agent**（按 L2/L3 发现改代码） | **可以 Sonnet 级** |
| L2 reviewer / L3 evaluator | **必须 opus 级** |
| 你自己（编排者） | **必须 opus 级** |

**为什么偏偏 Builder 可以**：它拿到的任务书已经把文件、步骤、验证命令写死了 ——
这是一个**收敛**任务，不是开放式判断。而且它写错会被 L1 卡住、被 L2 挑出、被 L3 打回，
**下游有三道门兜底**。省下来的算力是净赚。

反过来，`rd-spec` 的判据、`rd-plan` 的方案、L2 的审查、L3 的验收
**错了没有任何下游守卫能捕获**——它们本身就是守卫。所以那几处不许降档。

### Step 2 逐层派发

**同一 layer 的所有 Builder 必须在同一条消息里 spawn。**
一条消息多个 Agent 调用 = 真正并行；分成多条消息就退化成串行了。

**⛔ 下游 layer 的 prompt 不能照抄 `tasks.json` 的 steps。**

派 layer N 之前，先读 layer < N **实际产出的接口签名**（grep export / 函数定义），
把真实契约写进 prompt。

> 实跑教训：一个 Builder 为了防 Promise 永久 pending，在计划外多加了一个错误码。
> 下游负责错误码映射的 Builder 如果照抄 plan 阶段写死的 steps，就会漏掉这个分支。
> **计划是派发前写的，上游偏离是派发后发生的 —— 中间必须有你去对齐。**

每个 Builder 的 prompt **必须自包含**（队友不继承你的对话历史）：

```
你是 Builder，负责 {task.id}: {task.name}

## 工作目录
{绝对路径}

## 文件范围（⛔ 硬性规则）
你只能创建或修改以下文件：
{task.files 逐行列出}
严禁触碰其他任何文件。违反 = 任务失败。

## 上下文
{design.md 的「选定方案」和「契约变化」两节全文}
{本 task covers 的那几条 AC 的完整内容}

## 实施步骤
{task.steps}

## 测试先行
项目已有测试设施时：先写一个能表达 AC 的失败测试，再实现，直到它变绿。

## 变异测试（task.mutationTargets 非空时必做）
对 {task.mutationTargets} 里的每个文件，至少造 5 个变异体，**照下表机械地改，不要靠想象力**：

| 算子 | 怎么改 |
|---|---|
| 边界 | `<` ↔ `<=`，`>` ↔ `>=` |
| 布尔 | `&&` ↔ `\|\|`，删掉一个 `!` |
| 常数 | `n` → `n±1`，`0` → `1` |
| 守卫 | 删掉一个 `if` 早退 |
| 返回 | 提前 return，或返回默认值 |

每造一个变异体就跑一次测试，然后**还原**。逐条报告：

```
变异测试 src/core/ema.ts
  M1 k 系数 2/(n+1) → 2/n        killed by "AC-1 斜坡夹具末值"
  M2 种子改用第一个收盘价          killed by "AC-1 n=3 完整输出"
  ...
  存活 0 / 6
还原后 sanity: pass 29 fail 0
```

**存活 > 0 就不算完成** —— 补测试杀掉它，或说明它是等价变异体（改了但行为确实不变）并给出理由。

**测试通过只说明「实现和测试一致」，不说明「实现是对的」。**
这一步是唯一直接检验「测试集够不够用」的手段。

## 完成前必须跑
{task.verify}
输出必须贴出来，不许只说"通过了"。

完成后标记任务 completed。
```

> **给编排者**：`mutationTargets` 的机械下限由 `validate-plan` 卡住
> （每个 machine 判定的 AC 必须有一个覆盖它的 task 声明非空 mutationTargets）。
> **但那是下限，不是上限。**规则按「AC 的判定方式」卡，
> 而变异测试的真实需求按「这个模块的正确性是不是只有测试能验」——
> 一个纯逻辑模块完全可能只被 agent 判定的 AC 覆盖，规则放行，而它恰恰最需要。
> 实跑里那个 6/6 变异体全存活的模块就是这种情况。**凡是纯计算/纯逻辑的，都写进去。**

### Step 3 等待与推进

- 派发后**立即等待**，停止你自己的一切读写和分析。
- 当前 layer 全部 completed → 在新消息中 spawn 下一 layer。
- Builder 报告冲突或卡住 → SendMessage 指导，不要自己动手写它负责的文件。
- **单个 Builder 超 10 分钟无进展**：取其部分结果，停掉它，把剩余工作
  拆成更小的 task 重新派，并在 `run.json` 记一笔。
- 全部完成 → `SendMessage({to: ..., message: {type: "shutdown_request"}})` 逐个关掉，
  然后进入审核闭环。

### 返回契约 —— 派出去有规矩，回来也必须有

**每个 agent 的完整报告写进文件，只返回一份有界摘要。**

在每个 prompt 里写死：

```
## 返回契约（硬要求）
完整报告写入 `.rd/features/{slug}/reports/{你的名字}.md`。
返回给我的内容**不超过 15 行**，只含：
- 状态：done / blocked / partial
- 改了哪些文件（只列路径）
- 关键数字（测试数、通过数、你实测到的核心值）
- **偏离本说明的地方**（有就一句话点出，没有就写「无」）
- 报告文件路径
⛔ 不要把命令输出、代码片段、推理过程贴进返回内容 —— 那些写进报告文件。
我需要细节时会自己去读那个文件。
```

**为什么**：子代理的全部价值是「把污染关进用完即弃的上下文，只让蒸馏后的结论回流」。
让完整报告原样倒回主上下文，**等于买了压缩又当场退光** —— 派发的成本照付，收益归零。

**这条同时保护复核纪律**：拿不到全文，你就只能顺着它给的路径和数字去抽查，
而不是把它读过的东西重读一遍。

### 深度锁

**Builder 不得创建子 agent。**reviewer 和 evaluator 也不得。整棵树只有两层。
这条防的是套娃派生 —— 它会让成本和不可预测性同时失控，而且没人说得清是谁改了什么。

### Step 4 边界核对 —— 由你做，不是由 Builder 自查

一层全部返回后，**你**逐个核对每个 Builder 是否越界。核对方式：

```
git diff --name-only          # 相对上一次冻结/提交的实际改动
```
拿这份清单去比 `tasks.json` 的 `files` 白名单。**同时检查字节层面**：
BOM、裸控制字节（` ` / ``）—— 这类缺陷 L1 和 L2 都看不见
（语法合法、diff 渲染后不可见），只有拿字节流比对才抓得到。

**⛔ 不要让 Builder 自己用 `git status` 确认边界。**

> 实跑教训：两个 Builder 各自跑 `git status` 自查，结论都是错的 ——
> 它们看到的是全部并行 Builder 加上编排者改动的叠加状态，却当成了自己的。
> 其中一个还把编排者改的文件误报成"来自并行进程"。
> **并行场景下没有任何 agent 能从仓库全局状态推断出自己的边界。**

**Builder 的自报是线索，不是证据。**

> 实跑教训：一个 Builder 正确诊断了「转义序列会被静默解码成裸控制字节」这个危险、
> 正确修了代码路径，然后**在解释这个修复的注释里原样重演了同一个 bug**，
> 并在报告里写下「文件里不再需要任何转义序列，没有重犯风险」—— 这句是假的。
> L1 过（注释里语法合法）、测试过（不影响行为）、L2 大概率漏（diff 渲染后看不见）、
> L3 必然漏（不影响任何 AC）。**只有编排者拿字节流核对才抓得到。**

### Step 4b 【A18】你自己的核对也要守规矩

上面说「Builder 的自报是线索不是证据」。**同一句话对你成立。**

判定链的最后一环 —— 你为了核对而临时写的那个脚本 —— 是整条链上**唯一没有守卫的地方**。
Builder 的产出过三层门，你的核对过零层。

> 实跑统计：编排者的临时核对脚本**七次出错**。
> 最危险的一类不报错也不崩溃，只是数字是错的 ——
> git 的 `--name-only` 放在 `--` 之后被当成文件路径，2 个文件被报成 14 个，
> 差点作为正确结果写进 `review-target.json`。
> 另有一次错误被 `catch` 静默吞掉，功能整个没生效而输出看起来完全正常。

宣布任何核对结论之前，三件事：

**① 证伪优先 —— 先证明这个核对能失败**

构造一个**已知应该失败**的输入，确认核对报了失败。报不出来，说明它没有判别力，
后面所有「通过」都不值钱。

这不是新发明：`check-ac` 的 `-MustMatch`（绿色必须证明真的看到了东西）、
变异测试（测试必须证明能失败）、反向断言 —— 框架已经在三个地方用了同一个原则，
**唯独你自己的核对没有这一步**。

**② 双路复算 —— 数字必须用两条独立路径算出来**

七次出错里，抓到它们靠的都是「换一条路再算一遍」：去掉管道重跑、把文件读回来、
用另一种方式数文件。**一个数字只有一条来源时，你没有任何办法知道它是不是错的。**

**③ 落盘 —— 命令原文 + 原始输出**

写进 `reports/orch-check-{标识}.md`，并在 `run.json` 的对应轮次里标注：

```json
"l1_verified_by": "orchestrator",
"l1_evidence": "reports/orch-check-r3.md"
```

`check-artifacts.js` 会检查：**标了 `*_verified_by` 且不是 `agent` 的，必须有对应的
`*_evidence`，且那个文件必须真的存在。**这是这条里唯一能被机械卡住的部分。

> **能卡住的和卡不住的**：机制只能保证「你的结论指得出证据」，
> 保证不了「你的结论是对的」—— **编排者上面没有人**（见 A13）。
> 所以这条的状态是**已缓解，未解决**。
> 落盘的价值在于把错误暴露的时间点从「事后复盘」提前到「下一次跑门」。

### 异构做不到时：换不了厂商，就换提示词的切入角度

**为什么「大号审小号」不算异构**：同一家的模型，训练数据与思维习惯高度重合 ——
它**犯错的倾向**和**看不见错的倾向**是同一个来源。
同厂家复审能抓到**手滑**（打错字、少个判断、逻辑绕晕），抓不到**盲区**。

> 实跑佐证：L2 审查者做得很认真（跑变异测试、逐字重放上轮变异体、自造新变异体），
> 抓到了真问题。但「检查命令换个 shell 结论会翻转」「冻结记录里的 commit 号其实是一段报错」
> 「『只读文档某两节』这条规则根本无法执行」——**这三条它一条都没抓到**，
> 全是编排者后来自己撞见的。它们不需要更聪明，只需要**一个不按这套思路想问题的人**。

⛔ **换个措辞不算换提示词。**必须真的换切入角度。

> **先看清哪些已经是默认的**：身份（「让这段代码在生产上出事」）、
> 姿态（先证伪）、输入（不给作者的意图辩护）、顺序（失败路径优先）
> 这四条**已经写进 `rd-review` 成为默认模板**，不需要你在 prompt 里再交代一遍。
> 实跑里它们抓到了那一轮价值最高的 finding，所以从可选项升成了默认项。
>
> 下表因此只剩**真正需要逐轮变化**的那一维：

| 维度 | 怎么换 |
|---|---|
| **切面** | 一轮沿数据流看，一轮沿失败路径看（异常 / 超时 / 空值 / 边界），一轮沿状态机看 |
| **读序** | 一轮从入口往下，一轮从最深的副作用往回推 |
| **假设** | 一轮假设输入全是恶意的，一轮假设依赖全部会超时 |

**跨轮不要重复同一个切面** —— 同一个模型沿同一条路走第二遍，
找到的还是第一遍那些东西。

**必须承认的局限**：换提示词换的是**搜索顺序**，不是**知识盲区**。
同一个模型不知道的事，换什么问法都还是不知道。

⛔ **换切入角度不等于可以降档。**这一节讲的是「同档位之间怎么制造差异」，
不是「用弱模型凑数」。审查者一律 opus 级 —— 换角度能改的是它往哪儿找，
改不了它认不认得出找到的东西。

**这是缓解，不是替代。**不许在 `run.json` 或报告里把它记成「异构审查已满足」——
本机其实有可用的跨厂商路径（`opencli chatgpt/gemini/deepseek ask`，均已登录），
只是还没接进流程。见 `ROADMAP.md` 第 1 条。

## 二、三层自动审核闭环

```
ROUND N (N = 1, 2, 3):

  L1 机械门 ── 零 LLM 成本，先跑，早失败早退出
     node <agentrd>/scripts/gate-l1.js -Feature {slug} -Round N
     ├─ FAIL → 把失败项和输出交给 fix agent（新 agent，干净上下文）
     │         修完重跑 L1。L1 内部最多重试 3 次，仍失败 → 熔断
     └─ PASS ↓

  L2 异构审查
     1. 冻结目标：
        node <agentrd>/scripts/freeze-target.js -Feature {slug} -Round N
        ⛔ 不要先跑 `git add -A`。freeze 自己会对**范围内**的未跟踪文件做
           intent-to-add（`git add -N`），新文件照样进 diff；而 `git add -A`
           在没有 .gitignore 的项目里会把 node_modules 整个暂存进审查目标。
        ✅ 冻完核对的是 **files 一栏和 diff 本身**，不是「未跟踪」那一栏：
           `git add -N` 是一次性的，第 2 轮起新文件已经在 index 里，
           「未跟踪」显示 0 是**正常的**（第一轮登记过了），不代表它们掉出了 diff。
           真正该看的是：本轮改过的文件是不是都出现在 files 里、
           diff 里有没有它们的内容行。
     2. 派一个 fresh reviewer（异构模型优先，与 Builder 不同厂商）
        它单轮执行 rd-review，只读，返回分级 findings
        ⚠️ 换不了厂商时，必须换提示词切入角度 —— 见下方「异构做不到时」
     3. reviewer 返回前你不得改动工作树
     ├─ blocking > 0 → fix agent 修 → 回 L1（不是回 L2，机械门必须重跑）
     └─ blocking = 0 ↓

  L3 场景验收 ── 防 overfit 的关键层
     0. 你先把服务启动好，只把 host:port 交给 evaluator
        （让它不必为了跑起来去读任何代码）
     1. 派一个 fresh evaluator 执行 rd-eval
     ✅ 给它：acceptance.json、一段业务背景、host:port、
              以及 acceptance-runbook.md（**存在的话必须给**）
     ⛔ 不给实现过程、不给 diff、不给测试代码、不给 design.md / tasks.json
     ⛔ 要求它在报告末尾附「隔离审计」：列出读过的每一个文件
     📗 第 1 轮验收者收尾时必须产出 acceptance-runbook.md（只写「怎么观察」）；
        后续轮次直接给它，别让每个验收者重新摸索一遍浏览器驱动和页面结构
     ├─ 任一 AC 不通过 → fix agent 修 → 回 L1，ROUND N+1
     └─ 全部通过 → ✅ 完成，进 rd-keep

ROUND > 3 → 熔断
```

### 为什么 L3 必须存在

只有 L1 + L2 的话，你会得到一个**测试全绿、review 全过、但功能是假的**交付物。

agent 极容易 overfit 到固定测试代码：加 mock、加 fallback、放宽断言，
一个功能装模作样就过了。而 L2 的 reviewer 看的是 diff，它看到测试是绿的，
很难判断这份绿是真的。

L3 的 evaluator 拿不到实现和测试，只拿到自然语言场景和一个跑起来的系统，
它只能真的去操作一遍。**这是唯一能识破"假绿"的一层。**

### 每一轮都用新 agent

reviewer、evaluator、fix agent，**每轮都新建，不复用上一轮的上下文**。
复用会导致"上下文污染越修越烂"—— 修了三轮的 agent 已经背了三轮的错误假设。

例外：**同一轮内因 findings 做的修复，复审沿用同一个 reviewer 的同一 session**，
以 follow-up 继续，并且它必须逐项报告 `resolved` / `unresolved` / `new findings`，
不许只核对旧 finding 打勾。

### 每一轮各审多大范围 —— 三层不一样，别一刀切

实跑里这三条是每个编排者各自摸索出来的，写在这里省得重摸，
也防止有人把 L2 做成每轮全量而白烧 token：

| 层 | 第 1 轮 | 后续轮 | 为什么 |
|---|---|---|---|
| **L1** | 全量 | **全量** | 零 LLM 成本，没有省的理由；增量跑反而会漏掉「改 A 弄坏 B」 |
| **L2** | 全量 | **增量**（自上次冻结以来的 diff）+ 对遗留 nit 的定向复查 | 上一轮已审过的代码没变就不必重读；变了的部分自然进增量 |
| **L3** | 全量 | **全量重跑** | evaluator 看不到实现，**没有能力判断「哪些 AC 不受本次修改影响」**，只能全跑 |

**L2 增量的前提**：`freeze-target` 每轮生成新的 `l2-round{N}.diff`。
如果两轮的 diff 逐字节相同，说明冻结机制坏了（见上面「未跟踪」那一栏），
此时的「增量」是空的，等于这一轮没审。

### 报告的必填小节 —— 派 agent 前把它抄进 prompt

reviewer / evaluator 写的报告要过 `check-artifacts.js` 的小节检查。
**这张表原本只存在于脚本里，写报告的人看不见**，于是每轮都靠撞门才发现缺哪节。
派它们之前先跑一次，把结果贴进 prompt：

```
node <agentrd>/scripts/check-artifacts.js -Sections
```

当前值（**以脚本输出为准**，两者不一致时改这里，不是改脚本）：

| 产物 | 必填小节 |
|---|---|
| `proposal`（方案） | 方案 / 关键取舍 / 被排除的路 / 风险 |
| `spec.md` | 要解决什么 / 范围 / 关键约束 / 已确认的决策 |
| `design.md` | 选定方案 / 技术选型 / 影响面 / 契约变化 / 被排除的方案 |
| **L2 报告** | 审查结论 / blocking / important / nit |
| **L3 报告** | 验收结论 / 逐条 / 收尾附录 |

外加：Markdown 产物末行必须是 `<!-- RD-DONE ... -->`；
JSON 产物（`tasks.json` / `acceptance.json`）用 `"_complete": true` 代替。
**小节有标题但正文是空的 / 只剩模板占位符，一律算没写。**

## 三、熔断

以下任一条件成立，**立即停止，不许继续对轮，不许宣称完成**：

| 条件 | 判定 |
|---|---|
| ROUND 超过 3 | 问题根深，方案层面就错了 |
| L1 连续重试 3 次仍失败 | 机械问题都修不好，别往下走了 |
| 连续 2 轮 L2 的 blocking findings 指纹相同 | 原地打转，修的不是根因 |
| 同一个 task 失败 2 次 | 换假设，不要第三次重试同一条路 |

### 第三种失败模式：agent 死于外部原因

**配额耗尽、API 报错、进程被杀** —— 这既不是"卡住"也不是"返回了坏结果"，
**不计入轮次，也不触发熔断**。

处理方式：
1. 记进 `run.json`，标明是外部原因
2. **不要盲目重发** —— 先确认外部条件是否恢复
3. 恢复后，如果这个 agent 是 reviewer，用 **SendMessage 续上同一 session**
   （它的上下文还在，重建成本白付），不要新建
4. 外部原因连续中断 2 次仍无法推进 → 停下来报告，交用户判断

> 实跑教训：reviewer 的复审刚开始就因会话配额耗尽被终止。
> 原熔断规则完全没覆盖这种情况 —— 按字面执行会把它算成一轮失败，
> 三次就熔断，而实际上一行代码问题都没有。

熔断时输出完整状态摘要：走到哪一轮、每轮的 findings 数、还剩哪些 AC 没过、
你判断的根因、建议（回 `rd-plan` 重新设计 / 缩小范围 / 补充 `spec.md`）。

**这是整条流水线上唯一会打断人的地方，它在异常路径上。**

## 四、状态

### 4.1 每轮结束：追加一行到 `run.json` 的 `rounds`

```json
{"round": 1, "l1": "pass", "l2": {"blocking": 2, "important": 5, "nit": 3},
 "l3": {"passed": 4, "failed": 2}, "fingerprint": "sha256:...", "ts": "ISO"}
```

`fingerprint` 是本轮 blocking findings 排序后拼接的哈希，用于熔断规则里的"原地打转"判定。

### 4.2 派 agent 之前：写 `run.json` 的 `inflight`

**中断可以发生在任何时刻。**不要去预估「这一步能不能一口气跑完」——
预估必然出错，而且预估这件事本身就是把环境参数（谁的配额、多大窗口）
烧进流程设计里。**要求不是「算准」，是「任何时刻都能从产物恢复」。**

所以：**派发之前**写 inflight，**拿到结果立刻**清空并把结果落进 `rounds`。

```json
"inflight": {
  "stage": "build", "round": 2, "startedAt": "...",
  "what": "并行派出 T4/T5/T6",
  "agents": [
    {"name": "T4", "role": "builder", "task": "T4",
     "files": ["src/pipeline.ts"], "dispatchedAt": "...",
     "reportPath": ".rd/features/{slug}/reports/t4-pipeline.md"}
  ]
}
```

**`inflight` 非 `null` 就意味着上一次运行被中断在这里。**

恢复时的固定动作，**顺序不能换**：

1. 跑 `scripts/check-artifacts.js` —— 它告诉你缺什么、有没有无主证据
2. 读 `run.json` 的 `inflight` —— 它告诉你当时有谁在跑、该产出什么文件
3. 逐个核对 `reportPath` 在不在、完不完整
4. **以产物为准，不以记忆为准。**上下文里"我记得已经做过 X"不算数

### 4.3 被中断 agent 的部分产物必须有归属

`inflight.agents[].reportPath` 存在但内容不完整 → 该 agent 的产出**不算数**，
它写进 `evidence/` 的东西要么在报告里明确认领（写清来源与可信度），要么删掉。

**不允许无主证据留在 `evidence/`。**实跑教训：两个被终止的 evaluator 留下 6 个证据文件，
其中一张截图看起来"正好是想要的东西"——
而无法确认它的采集前提，拿它当证据就会得出一个形式无懈可击、结论完全错误的判定。
`check-artifacts.js` 会点名这类孤儿文件。

## 硬门槛

- **你不许写产品代码**（10 行以内的机械修复除外）。
- **不许给 L2 reviewer / L3 evaluator 降档**。Builder 和 fix agent 可以用 Sonnet 级，
  审查和验收不行 —— 审查者比被审者弱等于没审，验收者弱则「假绿」没人识破。
- **L2 / L3 报告末行必须有 `<!-- RD-DONE ... -->`**，否则 `check-artifacts`
  按「审到一半被中断」处理，这一轮不算数。收到没有标记的报告，当它没返回，重派。
- **不许跳过 L1 直接派 reviewer**。机械门是零成本的，先跑它。
- **不许在 reviewer 返回前改动工作树**。目标动了这轮就作废。
- **不许把 L3 的 evaluator 和 L2 的 reviewer 合并成一个 agent**。
  看过 diff 的 agent 没法再当用户。
- **不许在 blocking 未清零时创建正式提交**。
- **声称完成前必须给出与声明相称的可核验证据**：L1 输出、L2 报告、L3 逐条判定。
  "应该可以"不算完成。
