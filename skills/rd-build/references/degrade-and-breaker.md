# 降级、熔断与外部原因中断

> 📎 从 `skills/rd-build/SKILL.md` 抽出。**加载条件**：Step 1 首次选并行载体 / 载体降级 / 熔断 / agent 死于外部原因时。
> 不读会：Step 1 不知道 B 档派发失败时该降 C 串行继续、还是停下问用户，
> 也不知道「降级时告知一句然后继续、不要停下来问」—— 在降级处停下来问用户；
> 异常路径上该熔断的继续对轮白烧预算，外部中断被算成失败轮次三次就误熔断。

## 选并行载体（两档）

选并行载体，**用得上哪档就用哪档，不要跳级也不要预判失败**：

| 档 | 条件 | 说明 |
|---|---|---|
| **B. 并行子 agent** | 总是可用（默认） | 同一条消息里派多个独立 agent，各有干净上下文。**没有共享任务列表、不能互相通信**，全靠你编排 |
| **C. 串行** | B 档派发失败（比如环境禁止并行） | 你自己按 layer 顺序实现 |

B 档的编排规则固定如下（同消息派发、文件白名单、立即等待、深度锁 1 层），
跨任务的协调必须全部经过你。降级时告知用户一句，然后继续，不要停下来问。

## 熔断

以下任一条件成立，**立即停止，不许继续对轮，不许宣称完成**：

| 条件 | 判定 |
|---|---|
| ROUND 超过 3 | 问题根深，方案层面就错了 |
| 修复→复审循环每轮 2 次仍失败 | 同一处反复修不好，别往下走了 |
| 连续 2 轮审查层的 blocking findings 指纹相同 | 原地打转，修的不是根因 |
| 同一个 task 失败 2 次 | 换假设，不要第三次重试同一条路 |

熔断时输出完整状态摘要：走到哪一轮、每轮的 findings 数、还剩哪些 AC 没过、
你判断的根因、建议（回 `rd-plan` 重新设计 / 缩小范围 / 补充 `spec.md`）。
**这是整条流水线上唯一会打断人的地方，它在异常路径上。**

## 修复闭环：回唤 owner + 审查层复审

**回唤 owner 在新设计里才安全**：Builder 不写测试，测试失败 = 一个与 Builder 无关的
外部信号。它没有改测试的能力和动机（审查层写的测试它碰不着），造假风险消失。
旧框架用 fresh fix agent（干净上下文防作弊）的前提「Builder 同时是代码+测试作者」已不存在。

### 分流规则

| 失败类型 | 处置 |
|---|---|
| 局部失败（漏判空、边界、小 bug） | **回唤失败文件的 owner Builder**（SendMessage 续 session，省重读全代码的 token/time） |
| 方向性失败（审查层 blocking 带 `contract-break` / `wrong-result-silent`） | 换 fresh agent 或熔断 —— 回唤 owner 对新方案没有新视角 |
| 同一处二次失败 | 走现有熔断「同一个 task 失败 2 次 → 换假设」 |

**owner 定位**：按失败文件反查 `run.json` 的 `inflight.agents[].files` 白名单 ——
机械可查，跨任务破坏也能定位对（T5 搞坏了 T1 的文件，owner 是 T1 的 Builder）。

**防「为错误测试扭曲正确代码」**：回唤 owner 的指令里写死 ——
「如果代码看起来正确、但测试期望的是另一回事，**不要改代码让它绿**，
把测试失败原文带回来」。否则 owner 最自然的反应是改到绿，
而那个测试可能是审查层写错的。

### 审查层复审以 spec 定责

> 以 spec 为准，不以实现为准，不以测试为准。
> - 修复后符合 spec、测试仍红 → **测试错**，审查层改自己的测试
>   （只朝 checkIntent 靠，红线：不许朝实现靠拢；-MustMatch 锚点是 plan 冻结的，
>   改不到锚点以下）。
> - 修复后不符合 spec → **代码错**，owner 再修。
> - 两者都符合 spec 却失败 → 不可能，说明测试断言与 spec 对不上，仍判测试错。

**收敛保护**：修复→复审循环每轮 ≤2 次，超了走熔断。
变异只在修复**碰到 mutationTargets（full）文件**时才重跑，没碰不重跑。

## 第三种失败模式：agent 死于外部原因

**配额耗尽、API 报错、进程被杀** —— 这既不是"卡住"也不是"返回了坏结果"，
**不计入轮次，也不触发熔断**。

处理方式：
1. 记进 `run.json`，标明是外部原因
2. **不要盲目重发** —— 先确认外部条件是否恢复
3. 恢复后，如果这个 agent 是 reviewer，用 **SendMessage 续上同一 session**
   （它的上下文还在，重建成本白付），不要新建
4. 外部原因连续中断 2 次仍无法推进 → 停下来报告，交用户判断

> 实跑教训：reviewer 的复审刚开始就因会话配额耗尽被终止。
> 原熔断规则完全没覆盖这种情况 —— 按字面执行会把它算成一轮失败，
> 三次就熔断，而实际上一行代码问题都没有。
