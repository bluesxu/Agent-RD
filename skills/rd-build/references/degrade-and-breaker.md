# 降级、熔断与外部原因中断

> 📎 从 `skills/rd-build/SKILL.md` 抽出。**加载条件**：Step 1 首次选并行载体 / 载体降级 / 熔断 / agent 死于外部原因时。
> 不读会：Step 1 不知道 A 档启用条件与「TeamCreate 不存在 → 降到 B 不是 C」、
> 「降级时告知一句然后继续、不要停下来问」—— 直接降 C 丢并行，或在降级处停下来问用户；
> 异常路径上该熔断的继续对轮白烧预算，外部中断被算成失败轮次三次就误熔断。

## 三档降级的完整逻辑（为什么 B 档存在）

选并行载体，**用得上哪档就用哪档，不要跳级也不要预判失败**：

| 档 | 条件 | 说明 |
|---|---|---|
| **A. Agent Teams** | `TeamCreate` 工具存在 | 队友有共享任务列表、可互相通信 |
| **B. 并行子 agent** | 总是可用 | 同一条消息里派多个独立 agent，各有干净上下文。**没有共享任务列表、不能互相通信**，全靠你编排 |
| **C. 串行** | 前两档都不行 | 你自己按 layer 顺序实现 |

**`TeamCreate` 不存在或实际返回错误 → 降到 B，不是直接降到 C。**
（原设计只有 A 和 C 两档，而 `TeamCreate` 在很多环境根本不存在 —— 直接降级串行会白白丢掉并行能力。）

B 档与 A 档的编排规则**完全相同**（同消息派发、文件白名单、立即等待、深度锁 1 层），
唯一区别是队友之间无法通信，所以**跨任务的协调必须全部经过你**。
降级时告知用户一句，然后继续，不要停下来问。

## 熔断

以下任一条件成立，**立即停止，不许继续对轮，不许宣称完成**：

| 条件 | 判定 |
|---|---|
| ROUND 超过 3 | 问题根深，方案层面就错了 |
| 测试层连续重试 3 次仍失败 | 机械问题都修不好，别往下走了 |
| 连续 2 轮审查层的 blocking findings 指纹相同 | 原地打转，修的不是根因 |
| 同一个 task 失败 2 次 | 换假设，不要第三次重试同一条路 |

熔断时输出完整状态摘要：走到哪一轮、每轮的 findings 数、还剩哪些 AC 没过、
你判断的根因、建议（回 `rd-plan` 重新设计 / 缩小范围 / 补充 `spec.md`）。
**这是整条流水线上唯一会打断人的地方，它在异常路径上。**

## 第三种失败模式：agent 死于外部原因

**配额耗尽、API 报错、进程被杀** —— 这既不是"卡住"也不是"返回了坏结果"，
**不计入轮次，也不触发熔断**。

处理方式：
1. 记进 `run.json`，标明是外部原因
2. **不要盲目重发** —— 先确认外部条件是否恢复
3. 恢复后，如果这个 agent 是 reviewer，用 **SendMessage 续上同一 session**
   （它的上下文还在，重建成本白付），不要新建
4. 外部原因连续中断 2 次仍无法推进 → 停下来报告，交用户判断

> 实跑教训：reviewer 的复审刚开始就因会话配额耗尽被终止。
> 原熔断规则完全没覆盖这种情况 —— 按字面执行会把它算成一轮失败，
> 三次就熔断，而实际上一行代码问题都没有。
