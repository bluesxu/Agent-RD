# 策略：research-only —— 只调研，不写代码

> 适用：调研、方案对比、技术选型、"这个该怎么做"。
> 预算量级：**~5~10 万 token**
>
> **中断处理**：不要预估「能不能一口气跑完」—— 中断可以发生在任何时刻，预估必然出错。
> 要求是**进度持续落盘**：派 agent 前写 inflight，拿到结果立刻落盘，不要攒到阶段末尾一次性写。
> 恢复时跑 `scripts/check-artifacts.js`，**以产物为准，不以记忆为准**。
> **产物还要能自证写完**：每个文件的最后一个动作是盖收尾标记 `<!-- RD-DONE ... -->`
> （JSON 产物用 `"_complete": true`）。没有标记的一律按未完成处理 ——
> 「文件在」和「文件写完了」是两回事，中断留下的半截产物在前一个尺度上完全正常。

## 阶段

### 1. 界定问题 [required]

一次一个问题，问到能界定为止：

- 要在什么约束下选？（性能、依赖、团队熟悉度、部署环境、License）
- 有没有已经排除的选项？为什么排除？
- 结论要用来干什么？（马上实现 / 立项决策 / 只是了解）

**约束写不出来就不要开始调研** —— 没有约束的选型报告等于没有结论。

### 2. 多方案并行论证 [required]

派 **2~3 个异构 agent 独立调研**。硬性要求：

- **不继承主对话历史**，每个 prompt 自包含（把约束全文放进去）
- **异构优先**：同一个模型出三份方案，大概率是同一份方案的三种措辞
- **全部在同一条消息里派出**，然后**立即等待**，停止你自己的一切分析
- 每个 agent 的产出必须包含：**方案 + 关键取舍 + 它主动排除了哪些路及原因 + 风险**
- 涉及现有代码的结论必须带 `file:line`

### 3. 仲裁 [required]

逐条对照第 1 步的约束打分。

- 复核事实**顺着它给的 `file:line` 抽查**，不要把它读过的东西重读一遍 —— 那样这次派发就白费了
- **分歧本身要写进结论**，不要只留胜出的那个。三个月后回来，你需要知道当时为什么没选另一条路

### 4. 产出

一份文档，结构固定：

```markdown
# {问题} — 选型结论

## 约束
{第 1 步问出来的，逐条列}

## 结论
{一句话}

## 对比
| 方案 | 优 | 劣 | 是否满足约束 |

## 被排除的方案
{每条：方案 + 排除理由。这一节不许为空}

## 分歧记录
{三份方案在哪些点上不一致，各自理由}

## 未决风险
```

放哪里由用户定；有 `.rd/` 就放 `features/{slug}/research.md`。

## 硬门槛

- **不写任何产品代码。**需要验证某个方案可行时，写在临时目录里，验完删掉，并在报告里说明。
- **论证 agent 深度锁 1 层**，不得再派生子 agent。
- **不许派了不等。**
- **「被排除的方案」不许为空。**只出一个方案说明没有真的并行论证。

## 本策略的加载清单

**会用到**
- `skills/rd-plan/references/fanout-angles.md` — 多方案并行调研的角度差异化
- `skills/rd-plan/references/prompts/planner.md` — 派调研 agent（role=forward）
- `skills/rd-plan/references/arbitration.md` — 调研收齐后的仲裁
- `skills/rd/references/out-of-flow.md` — 流程外动作时

**永不加载**
- `skills/rd-spec/` — 本策略不建 spec / acceptance
- `skills/rd-build/` — 本策略不写代码，无审查层/测试层/验收层闭环
- `skills/rd-review/` — 本策略无代码可审查
- `skills/rd-eval/` — 本策略无场景可验收
- `skills/rd-keep/` — 本策略不沉淀实现经验（调研结论是交付物，不是 lessons）
