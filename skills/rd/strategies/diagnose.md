# 策略：diagnose —— 先复现，再修

> 适用：M 级以上的 bugfix（S 级 bug 走 `direct`）。
> 预算量级：**~5~15 万 token**
>
> **中断处理**：不要预估「能不能一口气跑完」—— 中断可以发生在任何时刻，预估必然出错。
> 要求是**进度持续落盘**：派 agent 前写 inflight，拿到结果立刻落盘，不要攒到阶段末尾一次性写。
> 恢复时跑 `scripts/check-artifacts.ps1`，**以产物为准，不以记忆为准**。

## 核心原则

**没复现就不许开修。**

一个改不对的 bug 修复，最常见的根因不是技术能力，是**修的不是那个 bug**。
先写一个必然失败的测试，是唯一能证明"我理解了这个问题"的方式。

## 阶段

### 0. 只问复现条件 [required]

不要走完整拷问。只问到能复现为止，一次一个问题：

- 什么输入 / 什么状态下发生？
- 期望是什么，实际是什么？
- 每次都发生，还是偶发？偶发的话有没有规律？
- 什么时候开始的？（有没有对应的改动）

**用户答不出复现条件** → 说明这一步就是本次任务的主要内容，
先做定向调查（可以派 agent 并行探索多个假设），查到能复现为止。

### 1. 写一个失败的测试 [required]

把复现条件固化成一个**当前必然失败**的测试。

**贴出它失败的真实输出。**这是"我确实理解了这个问题"的证据。

写不出失败测试的两种情况：
- 复现条件还不够明确 → 回到上一步
- 这个问题不可测（比如纯性能、纯时序）→ 明确说明，改用可观察的度量替代

### 2. 定位根因

顺着失败测试往回查。**区分「现象」和「推测」，分开写。**

可以派 agent 并行探索多个假设 —— 每个 agent 一个假设，
返回时必须带 `file:line` 证据。这是 bug 调查里并行最划算的场景。

**同一条路径失败两次 → 换假设，不要第三次重试。**

### 3. 修，直到测试变绿

**只修根因，不顺手改别的。**范围外的问题记下来，不在这次改。

### 4. L1 → L2 [required]

- **L1**：新测试绿，且**既有测试一条都不许红**
- **L2**：派 fresh reviewer 异构审查。重点看：这个修复是不是只治了标，有没有别的路径也能触发同样的问题

blocking > 0 → 修 → 回 L1 → 再审。**最多 2 轮。**

### 5. 收尾

报告必须包含：
- 复现条件
- **根因**（不是"改了什么"，是"为什么会错"）
- 修法
- 失败测试从红到绿的真实输出

有值得沉淀的坑 → 调 `rd-keep`。**"某个坑已经踩过"是最值得进 lessons 的一类。**

## 不做什么

- 不做 L3 场景验收 —— bug 修复的验收标准就是那个失败测试本身
- 不做多方案并行论证 —— 除非根因不明，那属于"定位"阶段的并行探索

## 硬门槛

- **没有失败测试不许开修。**这是本策略唯一的硬门槛，也是它存在的理由。
- **不许为了让测试变绿而放宽断言。**
- **不许顺手修范围外的问题。**
