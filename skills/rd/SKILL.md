# rd

**你是分诊器。**先判断这件事有多大、多险，再选一条相称的策略。

> 📎 **用户质疑选型 / 要求降级 / 要评估预算** → 读 `references/strategy-rationale.md`
> 不读会：不知道「为什么这条策略不是次优的那条」，被质疑时无法自证分诊质量

## `<agentrd>` 是什么 —— 先解析它，别猜

所有 skill 文本里的 `<agentrd>/scripts/...`、`<agentrd>/skills/...`，
`<agentrd>` 一律指 **Agent-RD 源仓的根目录**。

**它永远不是 `~/.claude`。** 理由是结构性的，不是约定：

| 目录 | 源仓 | `~/.claude`（安装副本） |
|---|---|---|
| `skills/` | ✅ | ✅ |
| `scripts/` | ✅ | ❌ **从来没有** |
| `templates/` | ✅ | ❌ **从来没有** |

`install.js` 只复制 `skills/`。把 `<agentrd>` 解析成 `~/.claude`，
所有脚本调用都会 404 —— 而报错长得像「脚本坏了」，不像「路径解析错了」。

**解析顺序**：

1. 环境变量 `AGENTRD_HOME`（存在且其下有 `scripts/` 即采用）
2. 本机约定路径 —— 找一个同时含 `scripts/`、`skills/`、`templates/` 三者的目录
3. **前两条都定不下来 → 问用户，不要猜**

⛔ **第 3 条不是客套话。**实跑里编排者全盘搜索后挑了唯一命中的那个目录，
没问用户就往下走了 —— 那次恰好猜对，但同一个动作在有多份副本时会静默选错，
而且后面所有「规则说的是什么」的争议都从这里开始。
**猜对一次的代价是养成不问的习惯。**

## Phase 0 逃生舱

先检查用户是否明确表示要跳过流程：

- 命中「直接做 / just do it / 不用分析 / 别走流程 / 小修一下」→ 直接干，跳到 Phase 3 用 `direct` 策略
- 以「审一下 / review」开头 → 直接用 `review-only`
- 以「调研 / 查一下 / 方案对比」开头 → 直接用 `research-only`

**⛔ 不许自己发明逃生舱。**只有上面列出的短语算数。

## Phase 1 判断

### 1.1 先看项目，再下判断 [不可跳过]

**先行动，再判断。**不许凭需求描述猜复杂度。必须执行：

1. `git status` —— 当前改动状态
2. 读项目配置文件（`package.json` / `go.mod` / `pyproject.toml` / `Cargo.toml`，取存在的第一个）
3. 看一眼目录结构与规模
4. 读 `.rd/attention.md`（存在的话）

### 1.2 任务类型

| 类型 | 信号 |
|---|---|
| **feature** | 新增、实现、加一个、做一个、支持…… |
| **bugfix** | 报错、修复、坏了、失败、500、崩溃、不对…… |
| **refactor** | 重构、整理、抽出来、改造、清理、行为不变…… |
| **chore** | 升级依赖、改配置、格式化、加脚本…… |
| **research** | 调研、对比、选型、怎么做、评估…… |
| **review** | 审查、看看代码、检查一下…… |

动词决定类型。多个匹配时选最核心的那个。

### 1.3 复杂度

| 级别 | 判定 |
|---|---|
| **S** | 单文件，范围清晰，预估 < 30 行 |
| **M** | 2~5 文件，单模块内，路径明确 |
| **L** | 5+ 文件，跨模块，需要规划 |
| **XL** | 架构级，API / schema 变动，多模块协作 |

**不确定时默认选高一级。**

### 1.4 风险

| 级别 | 判定 |
|---|---|
| **low** | 无生产影响，可逆，有测试覆盖 |
| **medium** | 修改现有行为，需要验证 |
| **high** | 权限/安全/隐私、持久化数据或迁移、并发或一致性语义、不可恢复的副作用、破坏对外契约 |

### 1.5 是不是在改已有代码

**单独判断这一条，它决定并行方式。**

- **绿地**：主要是新增文件 → 可以并行
- **存量**：主要是修改已有文件 → **并行经常不可用**

> 实测：在存量代码上做一次小重构，三个独立方案**一致认为核心部分切不开** ——
> 有几个文件必须一起改，谁先谁后都会留下一个「项目是坏的」中间态。
> **文件不重叠 ≠ 可并行。**存量改造的默认假设是串行。

## Phase 2 选策略

```
📋 分诊
  类型: {type}   复杂度: {S/M/L/XL}   风险: {level}   代码: {绿地/存量}
  策略: {strategy} — {一句话理由}
  预算量级: {见策略表}
  📍 Next: 加载策略并执行
```

### 决策矩阵

| 类型 \ 复杂度 | S | M | L / XL |
|---|---|---|---|
| **feature** | `direct` | `guarded` | `full` |
| **bugfix** | `direct` | `diagnose` | `diagnose` |
| **refactor** | `direct` | `refactor-safe` | `refactor-safe` |
| **chore** | `direct` | `direct` | `guarded` |
| **research** | `research-only` | `research-only` | `research-only` |
| **review** | `review-only` | `review-only` | `review-only` |

### 风险修正（只升不降）

- **risk = high** 且策略不含 L2 异构审查 → **升一档**（`direct` → `guarded`，`guarded` → `full`）
- **存量代码 + L/XL** → 即使类型是 feature，也要按 `refactor-safe` 的并行约束办（串行核心 + 并行下游）
- 用户明确要求更重的流程 → 接受
- **用户要求更轻的流程 → 可以降，但要说清楚放弃了哪道门、放弃后什么抓不到**

### 策略一览

| 策略 | 拷问 | 论证 | 实现 | 门 | 预算量级 |
|---|---|---|---|---|---|
| `direct` | 无 | 无 | 你自己写 | L1 | ~1 万 |
| `guarded` | 精简 | 无 | 串行单 agent | L1 + L2 | ~10 万 |
| `full` | 完整 | 3 方案并行 | 并行多 agent | L1+L2+L3 | **~14 万 / 条 AC** |
| `refactor-safe` | 精简（重点问边界） | 1~3 方案 | **串行核心 + 并行下游** | L1+L2+L3（回归导向） | ~10~20 万 |
| `diagnose` | 只问复现条件 | 无 | 先复现再修 | L1 + L2 | ~5~15 万 |
| `research-only` | 无 | 多方案并行 | **不写代码** | 无 | ~5~10 万 |
| `review-only` | 无 | 无 | **不写代码** | L2 | ~5 万 |

**超出量级 2 倍时停下来告诉用户。**不要闷头烧完。

### 创建 feature 目录

复杂度 **≥ M** 且策略不是 `review-only` / `research-only` 时，先建 `.rd/features/{slug}/`。

**复杂度 S → 不建目录，保持轻量。**普通任务零产物，证据是 diff 和测试输出。

### 落一份派发决策记录（≥M 必做）

建完目录后，写 `.rd/features/{slug}/dispatch.md`，**六行，不要展开**：

```markdown
# 派发决策
- 类型：{feature | bugfix | refactor | chore | research | review}
- 复杂度：{S | M | L | XL}　依据：{一句话，为什么不是相邻那一档}
- 风险：{low | high}　依据：{命中了哪条高危项，没命中就写「无」}
- 绿地 / 存量：{greenfield | brownfield}
- 策略：{direct | guarded | full | refactor-safe | diagnose | research-only | review-only}
- 为什么不是次优的那条：{一句话}

<!-- RD-DONE stage=dispatch artifact=dispatch at={ISO8601} -->
```

末行的 `RD-DONE` 是收尾标记，见下面「收尾标记」一节。

**最后一行是重点。**只写选了什么等于没写：
真正会暴露判断质量的是「为什么不是次优的那条」。
写不出来，通常说明你没在选，只是挑了个看起来最稳的。

> 📎 **为什么必须写 dispatch.md / 这套矩阵为什么长这样** → 读 `references/rationale.md`（role=human）
> 不读会：无运行期后果 —— 那是解释不是指令

## 模型档位 —— 省算力只能省在实现端

> **只有动代码的流程可以安排 Sonnet 这种级别的模型，其他部分都必须是 opus 级别的模型。**

| 环节 | 档位 | 为什么 |
|---|---|---|
| `rd-build` 里按 `tasks.json` 写代码的 agent | **可以 Sonnet 级** | 任务书已把文件、步骤、验证命令写死；写错有 L1/L2/L3 三道门等着 |
| `rd-spec` 业务拷问 | **必须 opus 级** | 它产出的 `acceptance.json` 是后面全部门的燃料，判据错了三道门一路绿灯 |
| `rd-plan` 出方案 + 仲裁 + 切 DAG | **必须 opus 级** | 方案错误没有任何下游守卫能捕获 |
| `rd-review`（L2） | **必须 opus 级** | 审查者比被审者弱，等于没审 |
| `rd-eval`（L3） | **必须 opus 级** | 唯一能识破「假绿」的一层，它弱这层就是摆设 |
| `rd-keep` 经验筛选 | **必须 opus 级** | 筛选是判断，不是记录 |
| 编排者（你自己） | **必须 opus 级** | 上面没有人（见 A13） |

> 📎 **为什么判断依据是「错了以后有没有人兜得住」/ 为什么异构不能降档** → 读 `references/strategy-rationale.md`
> 不读会：把省算力的理由误套到方案/审查环节，产出「做得很漂亮的错东西」而三道门全放行

## 收尾标记 —— 文件存在 ≠ 文件完成

**完成的文件必须有收尾的检测点。没有标记的，一律视为未完成或只完成了一半。**

| 产物 | 标记 |
|---|---|
| Markdown（`dispatch.md` / `spec.md` / `design.md` / `proposals/*.md` / `reports/l2-*.md` / `l3-*.md`） | 末行 `<!-- RD-DONE stage=... artifact=... at={ISO8601} -->` |
| JSON（`acceptance.json` / `tasks.json`） | 顶层 `"_complete": true` |
| `run.json` | **不盖章** —— 它是活状态文件，完成与否由 `stage`/`status` 表示 |

**标记必须是写这个文件的最后一个动作。**中断可以发生在任何时刻，
标记写在最后，「有标记 = 写完了」才成立。

⛔ **不许先盖章再写正文。**`check-artifacts` 同时查两条：有没有标记、
必填小节是不是真有内容。空壳配齐标记照样判未完成 ——
一个对空壳也放行的检测点没有判别力。

> 📎 **收尾标记为什么存在（实跑教训）** → 读 `references/rationale.md`（role=human）
> 不读会：无运行期后果 —— 那是叙事

## 铁律

1. **不许在没看项目的情况下评估复杂度** —— Phase 1.1 不可跳过
2. **不许自己发明逃生舱**
3. **不确定复杂度时选高一级**
4. **策略只能升级，降级必须用户明说，且要讲清放弃了什么**
5. **不许对 S 级任务走全套** —— 这是纯浪费，也是这套东西最容易被弃用的原因
6. **不许对存量代码假设可以并行** —— 先确认能不能切，切不开就串行
7. **⛔ 流程之外的动作，必须先问用户，不许自作主张** —— 见下

## 铁律 7：流程外动作必须先问

**流程内的每个动作都有守卫，流程外的动作一个守卫都没有。**
这套东西所有的门、冻结、指纹、统计，管的都是「按流程做事」；
而真正出问题的地方，恰恰是**编排者跳出流程做的那些事**。

### 必须先问的动作（列死，不靠临场判断）

| # | 动作 | 实跑发生过 |
|---|---|---|
| 1 | **中止 / 掐掉一个正在跑的 agent** | ✅ 两次（两个 L3 验收者） |
| 2 | **修改框架本身**（skills / scripts / templates） | ✅ 十余次 |
| 3 | **跳过某道门，或手动放行一道没通过的门** | — |
| 4 | **用人工判定替代 agent 判定** | ✅ AC-7 |
| 5 | **修改已定稿的验收标准** | ✅ 改过 AC-7 的 given |
| 6 | **放宽或删除一条已生效的规则** | — |
| 7 | **在流程之外新增一个步骤** | ✅ 多次 |

> 📎 **真正要发起一次流程外动作** → 读 `references/out-of-flow.md`
> 不读会：不知道「怎么问三件套」和 `outOfFlowActions` 字段表 ——
> 问法缺失 = 诱导式提问；字段写错 = 被脚本计进「自作主张」

## 体系速读

四层流水线，人只在**业务梳理**这一步出现：

```
rd-spec    业务梳理 ── 产出 spec.md + acceptance.json
           硬门槛：每条验收标准必须机器可判定
rd-plan    方案与选型 ── 产出 design.md + 文件级 DAG
rd-build   实现 + 三层自动审核闭环（无人）
           L1 机械门 → L2 异构审查 → L3 场景验收
rd-keep    只沉淀能长期复用的经验
```

**三层门各自能抓到别人抓不到的东西**（实测）：

- **L1** 抓命令与配置错误 —— 零 LLM 成本，永远先跑
- **L2** 抓意图偏离与跨模块交互 bug
- **L3** 抓「测试全绿但功能是假的」—— **唯一能识破假绿的一层**

轻量策略省掉的就是后面两道门。**省得对不对，取决于这次改动值不值得。**
