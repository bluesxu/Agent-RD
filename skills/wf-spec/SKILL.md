# wf-spec

把一句话需求变成两份东西：人读的 `spec.md`，和机器烧的 `acceptance.json`。

**这是整条流水线唯一需要人的地方。**后面的实现、审查、验收全自动，
它们能不能判断"做完了没有"，完全取决于这一步写出来的 `acceptance.json`。

## 开工

1. 读 `.workflow/attention.md`（存在的话）。
2. 按需求关键词检索 `.workflow/lessons/`，命中要报告来源路径。
3. 生成 slug（kebab-case，从需求核心词来），创建 `.workflow/features/{slug}/`。

## 第一步：拷问

**你的默认动作是提问，不是写文档。**

连续追问直到用户主动喊停，或你已经能填满下面每一类。
一次问一个，问完等回答再问下一个 —— 不要一口气抛十个问题，那会得到十个敷衍的答案。

必须问到的类别（每类至少一个具体问题）：

| 类别 | 要逼出什么 |
|---|---|
| **失败路径** | 输入非法、依赖挂了、并发撞了、超时了，分别怎么办 |
| **边界值** | 空、0、极大、超长、重复提交、乱序到达 |
| **权限与可见性** | 谁能做、谁能看、跨租户/跨用户怎么隔离 |
| **数据兼容** | 存量数据怎么办、schema 变不变、能不能回滚 |
| **不做什么** | 明确排除项 —— 这条最容易漏，也最容易让 agent 越界 |
| **判定方式** | 每条要求"你怎么知道它做对了" |

提问纪律：
- 用具体场景和边界案例检验理解，不要问"你还有别的要求吗"这种空问题。
- 用户说"你决定"时，给出你的建议和理由，让他确认，**不要静默替他决定**。
- 已经从 `lessons/` 或现有代码里能查到的事实，自己去查，不要问用户。

## 第二步：写 spec.md 和 spec-internal.md —— **两份，别写成一份**

结构固定，不要发挥。

### `spec.md` —— 需求本身。**L3 验收者会读它的全文**

```markdown
# {feature name}

## 要解决什么
{一段话，说清楚为什么要有这个能力，不是描述怎么实现}

## 范围
- 做：...
- 不做：...   ← 必须有，不许写"暂无"

## 关键约束
{性能、兼容、安全、依赖等硬约束，每条一行}

## 已确认的决策
{拷问过程中用户拍板的东西，带上理由}
```

### `spec-internal.md` —— 你的顾虑和打算。**L3 验收者禁读**

```markdown
# {feature name} —— 内部记录

> ⛔ 本文件对 L3 验收者不可见。理由见下。

## 未决风险
{知道但还没解决的，明确写出来，不要藏}

## 怎么确认算对了
{这东西最可能怎么静默出错？你打算靠什么抓住它？}
```

### 为什么必须分成两份

L3 验收者除了逐条验收，还要写一节**场外观察** ——
按普通用户的习惯去用，顺手撞见的怪事。**那一节的价值全在于「它是自己找到的」。**

而「未决风险」和「怎么确认算对了」这两节，本质上是**一份提示清单**：
它们直接告诉验收者「作者怕哪里错、打算怎么抓」。
验收者照着清单找到了，**什么都不证明**。

> 同一条道理在 `wf-eval` 里也写着：「⛔ 这里不举例。列出往期 evaluator 找到过什么，
> 会让下一个带着答案去找。」——那是防框架泄漏，这里是防需求文档泄漏，是同一件事。

**「关键约束」为什么留在 spec.md**：它是**规格**，不是提示。
一个测试者本来就该知道「这个值该怎么算、门槛是多少」——
实跑里验收者正是靠它才正确理解了输出里某一列的口径。禁它反而有害。

**为什么不用「只读某几节」的写法**：读文件的工具只能整读，
「只读两节」这条规则**根本无法被遵守** —— 实跑里验收者只能事后报备
「工具返回了整个文件，我实际看到了全部 75 行」。
**做不到的规则会腐蚀那些做得到的规则。**分成两份文件，规则才成立。

> 没有未决风险、也说不出「最可能怎么静默出错」时，`spec-internal.md` 可以不建。
> **但通常你说不出来只是因为还没想** —— 回去继续拷问。

## 第三步：写 acceptance.json —— 硬门槛在这里

从 `templates/acceptance.json` 起手。每条场景必须有 `judge`：

- `judge: "machine"` —— **必须**给出 `checkIntent`：说清**输入是什么、期望输出是什么、用什么判等**。
- `judge: "agent"` —— **必须**给出 `evidence`：验收 agent 要交回什么证据（`screenshot` / `recording` / `http-trace` / `log` / `file-content`）。

### ⛔ 这一步不许出现任何技术选型

**业务梳理只讨论业务。**`checkIntent` 里不许出现语言、框架、测试运行器、包管理器的名字
—— `node` / `npm` / `pytest` / `cargo` / `go test` / `jest` / `mocha` / `dotnet` 一个都不行。
`validate-plan -Stage spec` 会机械拦截。

**为什么这条是硬的**：技术选型是**阶段 1** 的事，而且阶段 1 会派 2~3 个 agent
（尽量不同厂商/不同模型）独立出方案再仲裁 —— 那套安排成本不低。
在阶段 0 写下一条 `node --test ...`，等于**在开会之前就把结论写在了纸上**。

> 实跑教训：三个论证 agent 里有两个，开口第一句就是
> 「技术栈其实不用论证，已经被钉死了」。它们看出来了，然后照常论证完 ——
> 整个阶段 1 的成本照付，产出的是一场走过场。

**对照**：

```
❌ node --test --test-name-pattern=feat\sAC-1
   ——「用微波炉加热 3 分钟」。加热多久是业务，用微波炉是技术。

✅ 对一组写死的输入跑计算，逐个断言四个周期的输出与手工验算值一致（相对误差 < 1e-9），
   并且能区分「用均值作初值」和「用首个数据点作初值」这两种实现
   —— 这条对 Node / Python / Go / Rust 方案同样成立。
```

**硬门槛（不可绕过）：**

> 一条验收标准如果既说不清 `checkIntent`（输入 / 期望输出 / 判等方式），
> 也说不清楚 agent 该拿什么证据来判定，
> 那它不是验收标准，是愿望。**回去继续拷问，直到它能被判定。**

判定不了的东西，后面没有任何一层能拦住 agent 说"我做完了"。

> **拷问力度不但没降，反而更狠了。**写一条 `node --test -t AC-1` 很容易蒙混过关 ——
> 它只证明你会写命令。而说清「给定这组输入，输出必须等于这组值，误差 < 1e-9」
> 逼你把**判据本身**想明白，那才是这一步真正要做的事。

**具体命令是阶段 1 的产物**：技术选定之后，`wf-plan` 会把每条 `checkIntent`
具化成选定栈的 `check` 命令。你在这里写下的不是占位符，是**它必须满足的规格**。

### 什么该 machine，什么该 agent

- **能写成断言的一律 machine**：状态码、返回结构、数据库最终态、错误码、性能阈值。
- **需要"像用户一样操作一遍"的才 agent**：多步交互流程、视觉呈现、跨页面状态、
  依赖真实外部服务的路径。

### 防 overfit 的写法

`judge: "agent"` 的场景，`then` 必须用**自然语言描述用户观察到的结果**，
不要写成代码断言，也不要提任何实现细节（函数名、文件名、变量名）。

原因：agent 极容易 overfit 到固定测试代码上 —— 各种 mock 和 fallback，
功能装模作样就通过了。自然语言描述的是目标本身，更难被曲解。
`wf-eval` 拿到这条场景时不会看到你的实现，它只能真的去跑一遍。

反例（不要这样写）：
```
"then": "loginHandler 返回 { code: 401 }"
```
正例：
```
"then": "页面停留在登录页，顶部出现红色提示「用户名或密码错误」，
        地址栏不变，且浏览器没有存下任何登录凭据"
```

## 第四步：校验并收尾

```powershell
powershell -ExecutionPolicy Bypass -File <agentflow>/scripts/validate-plan.ps1 -Feature {slug} -Stage spec
```

校验不过就按报错修，**不要手动跳过**。

通过后输出：

```
✅ 阶段 0 完成 — .workflow/features/{slug}/
   spec.md          {N} 项约束，{M} 项排除
   acceptance.json  {X} 条场景（machine {a} / agent {b}）
   📍 Next: 调用 wf-plan 进入技术选型
```

## 硬门槛

- **不许替用户做产品决策**。真实取舍必须让用户拍板，不因对话历史推断同意。
- **不许写出无法判定的验收标准**。写不出判定方式就继续问，这是本 skill 的唯一失败模式。
- **`spec.md` 的"不做"一节不许为空**。没有边界的需求，agent 一定会越界。
- 不创建 `.workflow/attention.md` 或 `lessons/` 条目 —— 那是 `wf-keep` 的事。
